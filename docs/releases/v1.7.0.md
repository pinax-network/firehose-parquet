# firehose-parquet v1.7.0

`v1.7.0` is a minor release of [v1.6.0](v1.6.0.md). New EVM datasets no
longer have the account-creation and system-nonce tables, which current EVM
Firehose blocks never fill. The retired Blast, NEAR and Tron network aliases
are removed, and StreamingFast credentials are read only when selected.
`recovery rebind --renamed` rebinds a dataset whose bucket was renamed in
place, and the writer exports its process memory and thread count on Linux.
Output formats, schemas and dependencies are unchanged. **An existing EVM
dataset with extended output must set `WITH_ACCOUNT_CREATIONS=true` and
`WITH_SYSTEM_NONCE_CHANGES=true` before it upgrades**: without them, `build`
refuses to resume it.

## Upgrade

- **Existing EVM datasets with extended output** (created by v1.6.0 or
  earlier; writers, backfill lanes and catch-up writers): set
  `--with-account-creations` (`WITH_ACCOUNT_CREATIONS=true`) and
  `--with-system-nonce-changes` (`WITH_SYSTEM_NONCE_CHANGES=true`) first,
  keeping `--with-gas-changes` (`WITH_GAS_CHANGES=true`) where it is set.
  Then move to the new image tag
  (`ghcr.io/pinax-network/firehose-parquet:1.7.0`). The datasets resume as
  they are, with the same tables, schemas and digests. v1.6.0 ignores both
  variables, so they can be set before the upgrade. Without them, `build`
  refuses to start and names each missing flag, before any Blocks request
  ([Opt-in tables](../chains/evm.md#opt-in-tables)).
- **New EVM datasets:** 15 tables with extended output, without the
  gas-change, account-creation and system-nonce tables. Leave the three flags
  unset unless those tables are wanted.
- **Other chains, and EVM without extended output:** nothing to do. The flags
  have no effect there, and `build` logs a warning when one is set.
- **`--network blast-mainnet`, `near-mainnet`, `near-testnet`, `tron` or
  `tron-evm`:** these are now refused at argument parsing. Pass the
  Firehose URL with `--endpoint` instead. A deployment that relied on
  `STREAMINGFAST_API_KEY` or `STREAMINGFAST_API_TOKEN` being read
  automatically must select it with `--api-key-envvar` or
  `--api-token-envvar` ([Authentication](../authentication.md)).
- **Maintenance and HyperLiquid reference jobs:** move to the new image tag.
  Nothing else changes. A listed table that a dataset doesn't have is
  skipped, as before.
- **Metrics:** two new gauges, `process_resident_memory_bytes` and
  `process_threads`, exported on Linux. There is nothing to configure.
- **Rollback:** v1.6.0 runs on datasets created by v1.6.0 or earlier. It
  ignores the two new variables. It always declares the account-creation and
  system-nonce tables, so it refuses an EVM dataset created by v1.7.0 without
  them. It also has the removed aliases again.

## Breaking changes

- **New EVM datasets no longer have `account_creations`,
  `system_account_creations` or `system_nonce_changes` (#743).** Current EVM
  Firehose blocks never fill them. Block version 4 and later record no account
  creations, and system calls change no nonce. On the public lake,
  `account_creations` has no rows after Pectra on Ethereum mainnet or after
  Pascal on BSC, and none on Base; the two system tables never had one.
  `--with-account-creations` (`WITH_ACCOUNT_CREATIONS=true`) and
  `--with-system-nonce-changes` (`WITH_SYSTEM_NONCE_CHANGES=true`) write them
  as before, with the same schemas and digests, like `--with-gas-changes`
  (#738). **Set both on every existing EVM dataset with extended output
  (writers and backfill lanes) before upgrading.** Without them, `build`
  refuses to start and names each missing flag, before any Blocks request.
  v1.6.0 ignores both variables, so they can be set before the upgrade. New
  EVM datasets with extended output have 15 tables
  ([Opt-in tables](../chains/evm.md#opt-in-tables)).
- **`--network blast-mainnet`, `near-mainnet` and `near-testnet` are removed
  (#735).** Their Firehose hosts no longer resolve. Pinax retired its Blast
  Firehose ([registry change](https://github.com/graphprotocol/networks-registry/pull/265)),
  and StreamingFast's NEAR hosts (`mainnet.near.streamingfast.io`,
  `testnet.near.streamingfast.io`) have no DNS record (checked 2026-11-27);
  the current registry lists no NEAR Firehose endpoint. To ingest from
  another Firehose for these chains, pass its URL with `--endpoint` and select
  its credential ([Authentication](../authentication.md)).
  Existing Parquet files and datasets still read by path (`fireparq
  inspect`), and NEAR blocks still decode.
- **`--network tron` and `tron-evm` are removed, and `STREAMINGFAST_API_KEY`
  and `STREAMINGFAST_API_TOKEN` are no longer read without a selector
  (#735).** Pinax does not serve or support Tron. The two aliases were the
  last built-in StreamingFast endpoints, so every built-in alias is now a
  Pinax host, and only Pinax hosts receive credentials automatically. To
  reach a StreamingFast Firehose, pass its URL with `--endpoint` and select
  its credential, for example `--api-token-envvar STREAMINGFAST_API_TOKEN`
  ([Authentication](../authentication.md)). Tron blocks still decode from a
  Tron Firehose given with `--endpoint`.

## New features

- **`fireparq recovery rebind --renamed` rebinds a dataset whose root was
  renamed in place (#635).** A bucket rename (Ceph RGW's `radosgw-admin
  bucket link --bucket-new-name`) or a local `mv` moves no data. It leaves
  nothing at the old root, so a rebind without `--renamed` has no copy to
  compare with and refuses ("holds no ingestion state", now naming the
  flag). With `--renamed` the rebind refuses unless nothing of the dataset is
  left at the old root: no local directory; on S3, no owner record in the
  old bucket, and no `state.json` or pending journal at the old root. On S3
  the new root must be the same prefix in another bucket. Every other check,
  the writes and the report are unchanged. A dataset can now change its
  bucket's name without a copy of the bucket. The bucket's policies and the
  readers' paths, Iceberg metadata included, still name the old bucket and
  are the operator's to move
  ([Renamed in place](../cursor-and-resume.md#renamed-in-place)).
- **Writer process RSS and thread count on Linux (#736, #723).** The
  metrics endpoint exports `process_resident_memory_bytes` and
  `process_threads`, read from `/proc/self/status` at each scrape, so memory
  outside the tracked buffers shows up beside the buffer estimates. At 64
  or more threads the writer also logs a `writer thread snapshot`, the
  thread names grouped by count, at most once every five minutes and over
  at most 256 threads ([Prometheus metrics](../metrics.md)). Nothing to
  configure; other platforms export neither.
