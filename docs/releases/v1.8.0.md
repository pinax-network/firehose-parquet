# firehose-parquet v1.8.0

`v1.8.0` is a minor release of [v1.7.0](v1.7.0.md). Two maintenance runs
that compact the same day no longer both commit it, so overlapping runs can
no longer put a day's rows in a table twice (#717). Tron support is removed
(#747). A SEC writer no longer stops on the disconnects of a quiet day, and
the idle flush also runs while `build` reconnects (#711). Help, the version
and completions run with a malformed env file (#637), and the unmaintained
`backoff` and `bincode` crates are replaced (#633). Output formats, schemas,
table digests and the dataset state are unchanged. **Move every job that
compacts a lake to v1.8.0 before letting maintenance runs overlap.**

## Upgrade

- **Maintenance jobs:** move every job that runs `fireparq maintenance` to
  the new image tag (`ghcr.io/pinax-network/firehose-parquet:1.8.0`),
  including the daily and weekly VACUUM jobs, which compact too. Nothing
  else changes: no new setting, and a lost race is still reported as a
  conflict and leaves the exit status 0. With every job on v1.8.0, two runs
  that compact the same day at once cost only the work of one of them
  ([Overlapping runs](../delta-maintenance.md#overlapping-runs)). A v1.7.0
  or older job that loses the race to a v1.8.0 one still commits the day
  again, so move a lake's jobs together, or suspend the old ones first.
- **Writers, backfill lanes and catch-up writers:** move to the new tag.
  Nothing changes for EVM, Solana, Bitcoin, Beacon, Antelope, NEAR,
  Cosmos or HyperCore. The reconnect back-off keeps its schedule, and the
  idle flush during a reconnect applies only with `--flush-idle-secs`,
  which no family but SEC sets by default.
- **SEC writers:** `--reconnect-stall-timeout-secs` now defaults to 129600 s
  for SEC. A `--reconnect-stall-timeout-secs 0` workaround can be dropped.
  An explicit value still wins.
- **Tron datasets:** v1.8.0 refuses to write them (`build`, `backfill`,
  `recovery recover` and `recovery rebind`). To keep writing one, stay on
  v1.7.0. Reading them, maintenance, `recovery status` and `recovery
  release` still work.
- **Rollback:** v1.7.0 runs on every dataset v1.8.0 writes, with the same
  schemas and state. A maintenance job rolled back to v1.7.0 brings back
  #717: keep its runs from overlapping.

## Breaking changes

- **Tron is no longer supported: the Tron decoder, `--block-type tron`, the
  `tron_base58` encoding and the Tron-style EVM profile are removed
  (#747).** Pinax does not serve or support Tron, and v1.7.0 removed its
  network aliases (#735). This corrects v1.7.0's note that Tron blocks still
  decode from a Tron Firehose given with `--endpoint`: they no longer do.
  - `--block-type tron` is refused as an unsupported block type, and
    `--block-type auto` refuses a Tron Firehose's `sf.tron.type.v1.Block`.
  - An endpoint whose chain name is `tron-evm` is now plain EVM: every byte
    field is `0x` hex, with no Tron Base58Check addresses. Write it into a new
    output root.
  - An existing Tron dataset, native `tron` or EVM written from a `tron-evm`
    endpoint (`tron_base58`), is refused by name: `build` does not resume it,
    and `backfill`, `recovery recover` and `recovery rebind` refuse it, each
    when it loads the dataset's state and before it writes a table or that
    state ("this dataset was written from Tron, which fireparq no longer
    supports"). On S3 the refusal leaves the bucket's owner record released,
    as any failure with no uncertain request does, so it needs no `recovery
    release` afterwards. `recovery status` and `recovery release` still work
    on it, `fireparq maintenance` still compacts, VACUUMs and checkpoints its
    tables (it reads only their Delta logs), and `fireparq inspect` still
    reads its files. Every Delta reader (DuckDB `delta_scan`, Polars
    `scan_delta`) still reads its tables, whose schema is in
    [v1.7.0's docs](https://github.com/pinax-network/firehose-parquet/blob/v1.7.0/docs/schemas/tron.md).
    To keep writing one, stay on v1.7.0.

## Fixes

- **Two maintenance runs that compact the same day no longer both commit it
  (#717).** delta-rs's conflict checker ignores `remove` actions with
  `dataChange: false`, which every OPTIMIZE writes. So up to v1.7.0, when two
  runs (the hourly job and the weekly full VACUUM, a run started by hand, or
  one job per group of tables) compacted a day from the same snapshot, both
  committed and the day's rows were in the table twice.
  - A compaction now commits with no delta-rs retry. When it loses the version
    race it reads the commits that won it:
    - one that removes a file of the day, or changes the table's metadata or
      protocol, is a conflict: the day commits nothing and the files it wrote
      are deleted;
    - one that adds a file it wrote is its own commit, sent again by the S3
      client after a lost response: committed;
    - anything else (the writer's appends, another day's compaction): the
      commit is tried again on top of it, up to 16 attempts in all.
  - The conflict is reported as before (`conflict: true` on its `date_error`
    line, the table's `conflicts`), and the run exits 0.
  - Overlapping runs are now safe, only wasteful (docs/delta-maintenance.md,
    "Overlapping runs"), once **every** job that compacts a lake runs this
    release. An older job that loses the race to a newer one still commits
    the day again, so upgrade or retire the old jobs first.
  - No duplicate was found on riv-dev1's eth, base and bsc (2026-10-12) or on
    riv-prod's (2026-11-27): no two active files of a day had overlapping
    `block_num` ranges, in any table. To check a lake whose runs may have
    overlapped, look for a `block_num` that appears twice in `blocks`
    (`SELECT block_num FROM delta_scan('…/blocks') GROUP BY 1 HAVING
    count(*) > 1`), and in each other table for two active files of one day
    whose `block_num` ranges share more than one block (two files that split
    a block share only that one).
- **A malformed `./.env` no longer breaks `--help`, `--version` or
  `completions` (#637).** The env file is loaded before the arguments are
  parsed, so before this fix a malformed `./.env`, or a missing
  `--env-file` / `FIREPARQ_ENV_FILE` path, failed `fireparq --help`, `-h`,
  `--version`, `-V`, `fireparq help`, a subcommand's `--help` and
  `fireparq completions <shell>` with `invalid env file …`. They now run as
  usual: help and the version print a stderr warning naming the file,
  `completions` stays silent. Every other command still fails on such a file
  before it reads or writes anything, as before.
- **A SEC writer no longer stops on two disconnects in a quiet day (#711).**
  `--reconnect-stall-timeout-secs` runs from the first failed reconnect until a
  message arrives, so its generic 900 s ended a healthy SEC writer with
  `reconnect stalled` when the stream dropped twice, 15 minutes apart, between
  two daily bursts. A SEC build now defaults it to 129600 (36 hours, as
  `--metrics-stale-after-secs`), when neither the flag nor
  `RECONNECT_STALL_TIMEOUT_SECS` sets it; the `--reconnect-stall-timeout-secs 0`
  workaround is no longer needed. The cap of 30 failed attempts without a
  message still stops a dead endpoint after 10 to 31 minutes, and still counts
  each disconnect of a quiet day: a gateway in front of firesec must not close
  idle streams more often than about once an hour
  ([SEC notes](../chains/sec.md)).
- **The idle flush also runs while `build` reconnects (#711).** With
  `--flush-idle-secs` (60 s for SEC), the rows of a burst were held until a new
  stream when the endpoint went down right after it; they are now committed
  once the stream has been quiet that long, reconnecting or not. A failed flush
  ends the run, as during a stream.
- **The idle-reconnect log prints `idle_for=120s` again (#711),** not
  `idle_for=Some(120s)`, on every chain.
- **The unmaintained `backoff` and `bincode` crates are replaced (#633).**
  Nothing changes for operators or data consumers; both advisories,
  RUSTSEC-2025-0012 and RUSTSEC-2025-0141, are no longer ignored in
  `deny.toml`.
  - The gRPC reconnect back-off is in-tree code with `backoff` 0.4's
    schedule as fireparq used it: 1 s, times 1.5 per attempt up to 60 s,
    each delay drawn from ±50 % of the interval, reset by a stream message.
  - The Solana vote filter decodes the Vote-program instruction itself, so
    `bincode` and `solana-vote-interface` leave the dependency tree (with
    `backoff`, 31 packages leave `Cargo.lock`). Before the switch, the new
    decoder agreed with the old one on 93 million generated and mutated
    payloads; `vote_transactions` and the other Solana tables are unchanged
    ([record](../audit/501-solana-vote-classification.md#decoder-without-bincode-633-2026-11-27)).

## Internal

- **SEC code cleanup (#711).** The SEC modules no longer allow dead code: the
  unused helpers are removed or test-only. Comments no longer point to a local
  `/tmp` specification or oracle. The 16 `#[ignore]`d tests that compared the
  mapper with the prototype on local sample days are removed, since
  `blocks/tests/sec_golden.rs` compares every column of every table with the
  prototype's rows on the golden fixture. The eight that checked the tests'
  mirrors against real filings now read those filings from the fixture and run
  in CI.
- **DuckDB 2.0.1 in CI (#749).** The DuckDB checks run with DuckDB 2.0.1 and
  its delta extension. The tests still accept DuckDB 1.5 or later, choosing
  `extension_directory` or 2.0's `extension_directories` by version, and
  read both profile layouts. `docs/development.md` and
  `docs/reading-tables.md` name the new pins.
