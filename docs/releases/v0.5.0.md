# firehose-parquet v0.5.0

`v0.5.0` is a focused but important minor release that improves the day-to-day operator experience in three visible ways:

1. the CLI binary is now shorter and easier to type: `fireparq`,
2. network selection is easier through built-in Firehose aliases, and
3. partition-related flags are more consistent and easier to understand.

It also includes a follow-up polish pass that updates the CLI help/examples to consistently present `--network` as the preferred path for Firehose-backed workflows while still keeping `--endpoint` available as an explicit override.

If you are newer to the project, this release is less about adding a huge new subsystem and more about making the tool easier to discover, easier to automate, and easier to teach to other people.

## Why this release matters

`v0.4.0` introduced a lot of powerful workflows around partition indexes and verification. `v0.5.0` smooths the operator experience around those capabilities.

This release helps by:

- reducing command length and friction for common workflows,
- making endpoint selection easier with `--network`,
- standardizing partition vocabulary so commands feel more predictable.

In other words: same engine, better controls.

## Highlights for new users

### 1. The installed CLI binary is now `fireparq`

The most visible change in `v0.5.0` is the CLI rename from `firehose-parquet` to `fireparq`.

What changed:

- the executable name is now `fireparq`,
- help text and examples use `fireparq`,
- release assets now package the `fireparq` CLI binary directly,
- the repository name and crate names still remain `firehose-parquet`,
- the Parquet file metadata namespace also still remains `firehose-parquet.*`.

This keeps the project identity stable while making the command itself much easier to type in daily use.

Release asset examples:

```bash
# macOS Apple Silicon
tar xzf fireparq-macos-aarch64.tar.gz
./fireparq-macos-aarch64/fireparq --help

# Linux x86_64
tar xzf fireparq-linux-x86_64.tar.gz
./fireparq-linux-x86_64/fireparq --version
```

Examples:

```bash
# Old mental model: same tool, shorter command
fireparq --help

# Build from source and run the new binary
cargo build --release --workspace
./target/release/fireparq --help

# Stream EVM blocks with the renamed CLI
fireparq \
  --endpoint https://eth.firehose.pinax.network:443 \
  --start-block 20000000 \
  --stop-block 20001000 \
  --output ./output
```

If you already had scripts using `firehose-parquet`, `v0.5.0` is the release where those scripts should be updated to call `fireparq` instead.

### 2. Built-in network aliases reduce endpoint copy/paste

`v0.5.0` adds built-in network endpoint aliases so you do not always need to type a full Firehose URL.

Instead of starting every run with a long `--endpoint https://...` value, you can often use `--network`.

Examples:

```bash
# Use a built-in network alias
fireparq \
  --network eth \
  --start-block 20000000 \
  --stop-block 20001000 \
  --output ./output

# Solana via alias
fireparq \
  --network solana \
  --start-block 250000000 \
  --stop-block 250001000 \
  --output ./output

# Still use explicit endpoints when needed
fireparq \
  --endpoint https://eth.firehose.pinax.network:443 \
  --start-block 20000000 \
  --stop-block 20001000
```

This is particularly helpful for:

- shell history readability,
- onboarding teammates,
- template scripts and docs,
- CI jobs where you want less repetitive endpoint boilerplate.

### 3. Per-network endpoint overrides are easier to manage

The network alias system also supports environment-variable overrides, which makes it easier to swap default endpoints without rewriting every command.

Example:

```bash
FIREHOSE_ENDPOINT_SOLANA=https://solana.internal.example.com:443 \
  fireparq \
  --network solana \
  --start-block 250000000 \
  --stop-block 250100000 \
  --output ./output
```

This is a nice fit for:

- internal staging endpoints,
- private infrastructure,
- different environments across dev/staging/prod.

### 4. CLI examples now consistently prefer `--network`

PR #229 follows through on the new network alias work by updating the CLI help and examples to show `--network` as the preferred operator workflow.

This does **not** remove `--endpoint`. Instead, it makes the intended usage clearer:

- prefer `--network` when a built-in alias exists,
- use `--endpoint` when you need an explicit override,
- if both are set, `--endpoint` still wins.

Examples:

```bash
# Preferred: use generated network defaults
fireparq --network mainnet --start-block 20000000 --stop-block 20001000

# Preferred: use generated Solana defaults
fireparq --network solana-mainnet-beta --start-block 250000000 --stop-block 250100000

# Explicit override still works
fireparq --endpoint https://eth.firehose.pinax.network:443 \
  --start-block 20000000 --stop-block 20001000

# Override a generated network with an env var
FIREHOSE_ENDPOINT_MAINNET=https://eth.internal.example.com:443 \
  fireparq --network mainnet --start-block 20000000 --stop-block 20001000
```

### 5. Canonical `chainName` handling is more predictable

Follow-up work in this release tightens network resolution so the exact Firehose `chainName` remains the canonical output for downstream logic.

For new users, the practical takeaway is:

- aliases are for convenience,
- canonical chain names are still what the tool ultimately uses internally and emits in metadata.

That means you get friendlier input without sacrificing consistent outputs.

### 6. Partition CLI vocabulary is more consistent

`v0.5.0` also standardizes partition-related flag naming so partition workflows are easier to reason about across commands.

The biggest user-facing change is in `partitions build`, where the build target granularity now uses a more consistent `--partition` flag instead of the older `--partition-types` wording.

Examples:

```bash
# Build a canonical partitions index with consistent partition naming
fireparq partitions build \
  --network eth \
  --start-block 10000000 \
  --stop-block 10020000 \
  --partition day,hour \
  --output ./output

# Write to S3 and emit the lookup sidecar
fireparq partitions build \
  --network eth \
  --start-block 10000000 \
  --stop-block 10020000 \
  --partition day,hour \
  --output s3://my-bucket/firehose \
  --write-lookup-sidecar \
  --json

# Resume an existing partition build
fireparq partitions build \
  --network eth \
  --start-block 10000000 \
  --stop-block 10040000 \
  --partition day,hour \
  --output ./output \
  --resume
```

That naming cleanup matters because partition workflows now span:

- build,
- resolve,
- shard,
- validate,
- partition-window ingestion,
- partition-aware cursor templates.

Small naming improvements go a long way when these commands are used together in automation.

## Updated examples for the newer CLI surface

Even though most of the big features landed in `v0.4.0`, here are the recommended `v0.5.0` forms using the renamed CLI and newer flag vocabulary.

### Ingestion examples

```bash
# EVM ingestion by built-in network alias
fireparq \
  --network eth \
  --start-block 20000000 \
  --stop-block 20001000 \
  --partition date \
  --output ./output

# Solana ingestion using alias + S3 output
fireparq \
  --network solana \
  --start-block 250000000 \
  --stop-block 250001000 \
  --partition date \
  --s3-bucket my-bucket

# Explicit endpoint still works and remains useful
fireparq \
  --endpoint https://eth.firehose.pinax.network:443 \
  --start-block 20000000 \
  --stop-block 20001000 \
  --bytes-encoding hex \
  --extended
```

### Partition index examples

```bash
# List partition rows
fireparq partitions ls \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour

# Resolve exact bounds for one partition
fireparq partitions resolve \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --partition-value '2015-07-30 15:00:00' \
  --partition-chain eth-mainnet

# Validate index continuity
fireparq partitions validate \
  --partitions-index ./output/eth-mainnet/partitions.parquet

# Deterministically shard work across workers
fireparq partitions shard \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --shard-count 4 \
  --shard-index 1
```

### Partition-window ingestion examples

```bash
fireparq \
  --network eth \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --partition-from '2015-07-30 14:00:00' \
  --partition-to '2015-07-30 18:00:00' \
  --partition-chain eth-mainnet
```

### Cursor-template example

```bash
fireparq \
  --network eth \
  --cursor-template 'cursor/{chain}/{partition_type}/{partition_value}.parquet' \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --partition-value '2015-07-30 15:00:00' \
  --partition-chain eth-mainnet
```

### Verify example using the renamed CLI

```bash
fireparq verify ./output/evm/mainnet/blocks \
  --chain evm \
  --table blocks \
  --profile standard
```

## Upgrade notes

If you are upgrading from `v0.4.x`, the most important changes are straightforward:

- update command invocations from `firehose-parquet` to `fireparq`,
- prefer `--network` when built-in aliases fit your workflow,
- update partition build automation to use the standardized partition flag vocabulary,
- keep in mind that metadata keys still use the `firehose-parquet.*` namespace.

If you maintain scripts, CI, or shell snippets, the binary rename is the one change most likely to require edits.
