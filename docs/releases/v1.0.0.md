# firehose-parquet v1.0.0

`v1.0.0` is the first major release of `firehose-parquet`. It writes every
table as a **Delta Lake** table, and it is the result of a full code audit of
the project (tracking issue #463): more than 110 pull requests merged since
`v0.7.2` fix data loss and crash-safety bugs, make the output schema
consistent and complete across chains, harden every command that writes to
local disk or S3, and replace plain Parquet directories with Delta tables
(#643).

**This is a breaking release: existing datasets must be rebuilt into a new
output root.** Almost every change alters the output format, an output
schema, a CLI default or the state that `fireparq` keeps next to a dataset.
Read the [upgrade guide](#upgrade-guide-read-first) before deploying.

## Summary

- **Delta Lake is the only output format.** Every table is a Delta table at
  `<root>/<table>/`, partitioned by `date` (`date=YYYY-MM-DD`). There is no
  format flag and no plain-Parquet mode. Each flush's parts are committed to
  the tables' logs byte for byte, with a `txn` marker per table and `blocks`
  last, so readers see only committed rows and can cut every table at the
  newest block of `blocks` for a consistent read. DuckDB `delta_scan` (1.5 or
  later) and Polars `scan_delta` are the supported readers, tested in CI. JVM
  engines are not a target (#643).
- **Crash recovery rolls forward exactly once.** `build` writes every flush as
  one all-table transaction with deterministic part names and output authority
  under `.fireparq-ingest/` (#468). Before any new block is requested, recovery
  rolls an interrupted transaction forward exactly once into each Delta table
  whose `txn` lacks it (#643). A crash, a failed write or a replay can no longer
  lose or duplicate rows.
- **Ownership that leaves the tables to maintenance.** `build` and `recovery`
  take dataset ownership, and it guards only fireparq's writer and its state
  (`.fireparq-ingest/`, `_fireparq/`). An off-the-shelf `deltalake` job
  compacts, vacuums and checkpoints the tables beside the running writer: the
  reference script `scripts/delta_maintenance.py` and the example CronJobs in
  `deploy/examples/`, tested in CI beside a real `build` (#636, #643).
- **Delta column types.** Signed integers with checked casts, `decimal(20,0)`
  for currency amounts and unchecked 64-bit values, `string` enums, UTC
  `timestamp` columns in microseconds that keep millisecond block times, and
  `date` as a partition value only, not a column of the files (#491, #643).
- **A final-only lake, one bucket per network.** `--output` is the dataset
  root as given, with an opt-in `{chain}` placeholder (#654), so one bucket per
  network holds its tables at the bucket root. The recommended deployment is one
  continuous final-only writer per network. It commits every
  `--flush-interval-secs` at the chain head and by size while it catches up
  (#659), and a restart lists no data however large the dataset has grown
  (#655).
- **One consistent schema across chains.** The canonical `timestamp` keeps
  millisecond block times everywhere, column names are unique, and every chain
  gains columns and tables that were dropped before (EVM withdrawals, access
  lists and EIP-7702 authorizations, Beacon execution requests, NEAR receipt
  actions and logs, Tron contracts, and more).
- **Failed transactions are modeled explicitly.** EVM includes failed
  transactions by default with only their persistent state changes; Solana,
  Tron, Antelope and NEAR rows carry their transaction or receipt outcome.
- **Provider-scoped credentials and explicit S3 destinations.** Firehose
  credentials are only sent to the provider they belong to, `.env` is read from
  the working directory only, and every S3 write needs an explicit
  `s3://bucket/prefix`.
- **Non-final streams stay a CLI capability.** `--final-blocks-only=false`
  writes an append-only event history in which every row carries
  `stream_ordinal`, the durable delivery order of its event, and a documented,
  tested `delta_scan` query returns the canonical chain head (#648). It is not
  part of the recommended deployment.
- **Removed.** `merge`, `truncate`, `scan`, `rollup`, the `partitions`
  subcommands and `partitions.parquet`; `verify`, which returns over Delta
  snapshots in #666; `--partition` and its finer layouts; `--cursor-template`;
  and the plain-Parquet output. See [Removed](#removed).
- **Performance.** Faster encoding on every chain, adaptive compressed file
  sizes, flush windows sized by the stream's pace, tuned gRPC receive windows
  and disk-spooled S3 uploads.

## Upgrade guide (read first)

### 1. Rebuild into a new output root

Do not point `v1.0.0` at a dataset written by `v0.7.x`. Build into a new, empty
output root (for example a new bucket per network, `--output
s3://ethereum-mainnet`, or `--output 's3://my-bucket/v1/{chain}'` next to your
existing `s3://my-bucket/v0`, which `v0.7.x` filled as
`s3://my-bucket/v0/<chain_name>/`) and keep the old root read-only until the
rebuild has caught up.

Every breaking change below needs that rebuild. `build` refuses to adopt or
resume a root written by an earlier release or a pre-release build, so none of
them can be applied to existing output in place:

| Change | Issues | `v0.7.2` | `v1.0.0` |
|---|---|---|---|
| Output format | #643 | Plain Parquet files, read by globbing a table directory | A Delta table per table at `<root>/<table>/`, read through its `_delta_log/`; nothing reads a table by walking its files |
| Partition layout | #652 | `year=YYYY/month=MM/date=DD/` by default, or another `--partition` layout | `<table>/date=YYYY-MM-DD/` only; `date` is the Delta partition column, not stored in the files |
| Output root | #654 | `--output` plus an appended `<chain_name>` directory | `--output` exactly as given, with an opt-in `{chain}` |
| Column types | #643 | Arrow types: unsigned integers, dictionaries | Delta types: checked `long` and `short`, `decimal(20,0)` for the columns each chain lists, `string` enums |
| Canonical `timestamp` | #491, #643 | `Timestamp(Second, UTC)`, written as a plain Parquet `INT64` | A Delta `timestamp`, `TIMESTAMP(MICROS, UTC)`, holding the block time to the millisecond |
| Schemas | #492, #495–#511, #550 | | Columns added, renamed and retyped, and tables added on every chain ([Schema changes by chain](#schema-changes-by-chain)) |
| Row selection | #494, #501, #550 | | EVM includes failed transactions, Solana vote filtering keeps administrative activity, Tron excludes failed smart-contract calls, Antelope keeps `onerror` handlers and scheduled transactions, and several index columns are renumbered |
| Non-final columns | #648 | `fork_step` | `fork_step` and `stream_ordinal` on every table of a non-final stream |
| Dataset state | #468, #647 | `cursor.parquet` selected the resume point | Output authority under `<root>/.fireparq-ingest/` binds the chain, mapper version (`fireparq-mapping-v3`), table schema digests, encoding, effective feature flags, layout and storage; `_fireparq/cursor.parquet` is an optional mirror. `build` refuses output without authority, and a legacy `cursor.parquet` |
| Derived artifacts | #643, #653 | `partitions.parquet`, `merkle_roots.parquet`, `verify_runs/` | None: no command writes or reads them |

A new root must be empty (on S3, only the owner record may exist) and must not
contain a cursor mirror.

Querying old and new data side by side: keep the two roots separate and
normalize the old files in the query. In DuckDB:

```sql
-- v0.7.x files: timestamp is BIGINT seconds and the day directory is date=DD.
-- Disable hive partitioning for the old tree so `date` stays the DATE column.
SELECT * REPLACE (to_timestamp("timestamp") AS "timestamp")
FROM read_parquet('s3://my-bucket/v0/mainnet/blocks/**/*.parquet', hive_partitioning = false)
WHERE block_num < 21000000
UNION ALL BY NAME
-- v1.0.0: a Delta table, read through its log; `date` is its partition column.
SELECT *
FROM delta_scan('s3://my-bucket/v1/mainnet/blocks')
WHERE block_num >= 21000000;
```

The glob is only for the old, plain-Parquet tree: never glob a v1.0.0 table.
`UNION ALL BY NAME` fills columns that only exist in the new files with `NULL`
for old rows. Only do this for tables whose existing columns kept their type
and meaning; check the per-chain tables below, and prefer rebuilding a range
over reconciling it in SQL. Some columns keep their type but change their
values, so a union will not flag them: Beacon
`execution_payload.base_fee_per_gas` (hex bytes before, a decimal string now),
NEAR `state_changes.block_id` / `parent_id` (hex before, base58 now), Solana
`rewards.reward_index` and every table where row selection changed. Select
columns by name, never by position.

### 3. Deployment notes

- **Recommended: a final-only lake.** Give each network its own bucket and run
  one continuous final-only `build` per network (the default
  `--final-blocks-only=true`, no `--stop-block`) with the dataset at the bucket
  root. There is no live bucket: non-final output
  (`--final-blocks-only=false`) remains a CLI capability, not a deployment this
  release recommends. Starting settings, from #659 and the #658 benchmark
  (measured before the Delta commits, which add about one PUT and one LIST per
  table with rows to each flush):

  | Setting | Value |
  |---|---|
  | `OUTPUT` | `s3://<network bucket>` (the bucket root) |
  | `FLUSH_INTERVAL_SECS` | `60` (60–120): the commit cadence at the chain head; suspended while catching up |
  | `FLUSH_BYTES` | `33554432` (32 MiB, the default): the file target while catching up |
  | `FLUSH_MEMORY_BYTES` | `268435456` (256 MiB, the default), or `1073741824` (1 GiB) for 2.5–3.5× faster catch-up at about 2.8 GiB peak RSS instead of 1.0 GiB |
  | Memory limit | Headroom above the peak RSS measured on Robinhood and Arbitrum One (about 1.0 GiB with the default trigger, 2.8 GiB with 1 GiB), for example 2 GiB and 4 GiB |
  | Maintenance | The `deltalake` CronJob hourly (`17 * * * *`, `concurrencyPolicy: Forbid`) and a weekly full VACUUM |

  With the default 256 MiB trigger a fast chain such as Robinhood flushes
  about every 27 s, so it never reaches a 60 s cadence: raise
  `FLUSH_MEMORY_BYTES` there. The README section "Recommended deployment"
  explains each setting.
- **Explicit S3 output (Kubernetes).** Replace `S3_BUCKET` plus a relative
  `OUTPUT` with an explicit URI. Kubernetes expands `$(VAR)` references to
  variables defined earlier in the same container:

  ```yaml
  env:
    - name: BUCKET_NAME
      valueFrom:
        configMapKeyRef: { name: fireparq, key: bucket }
    - name: OUTPUT
      value: s3://$(BUCKET_NAME)/v1
  ```

  Deployments that are not migrated exit with an error before writing. Keep
  `S3_BUCKET` only as a consistency check (it must match the `OUTPUT` bucket) or
  for read-only shorthand keys. Check the `resolved write destinations` log line
  after rollout.
- **One bucket per network (Kubernetes).** `OUTPUT` is the dataset root, so
  `OUTPUT=s3://$(BUCKET_NAME)` puts the dataset at the bucket root: a Delta
  table per table at `s3://ethereum-mainnet/<table>/` (its `_delta_log/` and
  its `date=YYYY-MM-DD/` data files), with `.fireparq-ingest/` and
  `_fireparq/` (the cursor mirror) beside the tables. To share one bucket between networks, use
  `OUTPUT=s3://$(BUCKET_NAME)/{chain}` instead.

  ```yaml
  env:
    - name: BUCKET_NAME
      valueFrom:
        configMapKeyRef: { name: fireparq, key: bucket }
    - name: OUTPUT
      value: s3://$(BUCKET_NAME)
  ```

  Choose it before the first run: the resolved root is part of the protected
  dataset identity, and a later run whose `OUTPUT` resolves inside or above the
  existing dataset (for example after adding or dropping `{chain}`) is refused
  before any Blocks request. The bucket must be empty
  for the first `build` (only the owner record may exist). Bucket-wide ownership (below) already means one writer per
  bucket, so one bucket per network also gives every network's `build` its own
  owner.
- **S3 ingestion needs explicit keys and an HTTPS endpoint.** Every S3 `build`
  (output or cursor) needs both `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`;
  the provider credential chain alone is not enough. A custom
  `--aws-endpoint-url` / `AWS_ENDPOINT_URL_S3` must be `https://` with a host
  (#520, PR #613). The check runs after EndpointInfo and before any S3 request;
  `--dry-run` skips it.
- **Writable temporary directory for the S3 upload spool.** S3 ingestion writes
  its upload spool to the system temporary directory (`$TMPDIR`, else `/tmp`);
  there is no separate flag. Each part is encoded to an anonymous spool file and
  verified through a second spool of the same size before it is committed, so
  plan for roughly two encoded parts of free space for every part in flight. With
  the default flush concurrency (#516) several parts can be in flight: encoded
  parts are bounded by `--flush-inflight-bytes` (256 MiB) and up to
  `--flush-publish-concurrency` (4) readback spools exist at once, so allow
  about 256 MiB plus 4 × the largest part (about 400 MiB with the 32 MiB
  default), more when a table outgrows the target. `--flush-inflight-bytes 1`
  brings it back to about two encoded parts. Kubernetes pods with
  `readOnlyRootFilesystem: true` need a writable volume there, for example an
  `emptyDir` mounted at `/tmp`.
- **S3 bucket requirements.** Mutating commands hold a persistent owner record,
  `.fireparq-owner-v1.json` at the bucket root. The bucket must support
  conditional writes (`If-Match` / `If-None-Match`) and object versions, and the
  credentials need read/write on `.fireparq-owner-v1.json` and
  read/write/delete below `.fireparq-owner-probes-v1/`.
- **One writer per output root, and on S3 one writer per bucket.** Each dataset
  has exactly one owner at a time: a second `build` or `recovery recover` on
  the same root, or on an ancestor or descendant
  directory, fails immediately instead of racing. On S3 the owner covers the
  whole bucket: a second mutating command on **any** prefix of the same bucket
  fails with `bucket ownership is held; there is no age-based or automatic
  takeover`. Give each concurrently running S3 writer (for example one `build`
  per network) its own bucket. The Delta tables are not the owner's: the
  `deltalake` maintenance job runs beside `build` without it (#636); the
  README ownership section gives both users' bucket policy.
- **When an S3 owner is kept after a failure (#640).**
  - `build` releases the bucket owner on exit, as a successful run does, when
    every request it sent had a definite outcome: failures before any mutation,
    failures after resolved mutations (including a failed transaction left
    pending, which the next `build` recovers before streaming), and HTTP
    401/403 refusals, which the provider did not apply. A first SIGINT/SIGTERM
    also releases it.
  - `build` keeps the owner after an ambiguous request (timeout, lost
    acknowledgement, connection reset, unverifiable readback, 5xx, 409/412),
    after a second signal (exit 130), after a panic, or when the release request
    itself fails. Its error then names the owner UUID and generation, why it was
    kept, and the exact `recovery status` and `recovery release` commands. A
    Delta log commit is the exception: its outcome is read from the table's
    `txn` at the next start, so an ambiguous one does not keep the owner
    (#643).
  - `recovery` still keeps the owner after **any** error, and logs the same
    guidance.
  - A kept owner makes every later writing command on the bucket fail until it
    is released: run `fireparq recovery status s3://bucket/prefix`, confirm that
    the old process is gone and that the provider has finished its requests,
    then run `fireparq recovery release` with `--expected-owner`,
    `--expected-generation`, `--stopped-writer-evidence` and
    `--provider-quiescence-evidence`. Process exit or elapsed time alone is not
    proof. Local outputs release their directory locks when the process exits.
- **Recovery.** A crash leaves a journal that the next `build` recovers before
  doing anything else. `fireparq recovery recover <path>` runs the same
  recovery offline for protected ingestion and the cursor mirror. `recovery`
  commands read `AWS_ENDPOINT_URL_S3` like every
  other command; `AWS_ENDPOINT_URL` is used only when neither
  `--aws-endpoint-url` nor `AWS_ENDPOINT_URL_S3` is set (#639).
- **Schedule the Delta maintenance job beside every writer (#643).** Without
  it, each table keeps one small file per flush and an ever longer log tail.
  Adapt `deploy/examples/delta-maintenance-cronjob.yaml` (hourly OPTIMIZE of
  closed dates, lite VACUUM, checkpoint and log cleanup; a weekly full VACUUM
  with the enforced 168 h retention), give it its own S3 user limited to the
  table prefixes, and alert on `firehose_parquet_delta_log_tail_commits` and on
  a writer that has been down for more than a day (README "Delta
  Maintenance").
- **Readers need a Delta reader.** Read each table through its log with DuckDB
  `delta_scan` (1.5 or later for S3: 1.1's `delta` extension fails anonymous
  reads once a table has a checkpoint) or Polars `scan_delta` with
  `deltalake`. A glob of a table's Parquet files reads compacted rows twice
  until VACUUM deletes the replaced files. For a consistent read across tables,
  take the newest `block_num` of `blocks` first and bound the other tables by
  it (README "Consistent reads across tables").
- **Local filesystems** must support atomic hard links and file and directory
  `fsync`, and directory ancestors must be readable (#578). Local ownership uses
  directory inode locks on macOS and Linux.
- **Temporary `.fireparq-txn-*.tmp` files** belong to a transaction in progress.
  Do not delete them by hand; the next `build` or `recovery recover` cleans them
  up.

  `ghcr.io/pinax-network/firehose-parquet-maintenance` next to the fireparq

## Highlights by area

### Delta Lake

Every table is a Delta table (#643; [design](../design/delta-lake.md)):

- **Protocol.** Reader version 1, writer version 2, no table features,
  `date` as the only partition column, `delta.appendOnly`, 7-day log and
  deleted-file retention, statistics on `block_num` and `timestamp`, and
  `fireparq.descriptor`, `fireparq.chain` and `fireparq.blockType` properties
  that bind each table to its stream. `build` creates every table of the
  stream at its first start, also tables that never get rows.
- **Commits.** fireparq keeps writing its deterministic `part-v1-*` files and
  commits each one byte for byte with an `add` action and a `txn`
  (`fireparq:<descriptor>`, the last accepted ordinal): one commit per table
  with a part, the other tables first and `blocks` last, before authority
  advances. The commits are blind appends, so maintenance can run beside the
  writer, and a second writer with the same `appId` fails instead of adding
  rows twice.
- **Recovery.** A transaction interrupted after its journal was Committed is
  committed to exactly the tables whose `txn` lacks it. Tables that already
  hold it are not read again, so a restart works after maintenance compacted
  and vacuumed their files.
- **Readers.** DuckDB `delta_scan` (1.5 or later) and Polars `scan_delta` read
  every table of every chain in CI, with `date` pruning and after a checkpoint,
  OPTIMIZE and VACUUM. JVM engines are not a target.
- **Maintenance.** `scripts/delta_maintenance.py` (`deltalake` 1.6.6) runs
  OPTIMIZE of closed dates, VACUUM, a checkpoint and log cleanup on a
  schedule, with example CronJobs in `deploy/examples/`.

### Ingestion safety

`v0.7.x` wrote each table on its own and saved `cursor.parquet` afterwards. A
failed table write could drop that table's buffer and still save the cursor
past the lost rows (#464), an unreadable cursor silently restarted ingestion
from genesis (#465), random part names duplicated data on replay (#468), and a
cursor save failure only logged a warning (#469).

In `v1.0.0`, every flush is one all-table transaction (#468):

1. the complete flush is validated, journaled and assigned deterministic
   `part-v1-*` names;
2. each part is staged, published and verified (locally with `fsync` and atomic
   publication, #578; on S3 with one conditional PUT and a readback, #520);
3. each table's part is committed to its Delta log, `blocks` last (#643);
4. the output authority under `.fireparq-ingest/` advances, then the optional
   `_fireparq/cursor.parquet` mirror.

A crash at any point is recovered before the next Blocks request: parts of an
uncommitted transaction are removed, a committed one is rolled forward (into
each Delta table whose log lacks it, gated by the table's `txn`, #643), and the
replayed window republishes identical names. On mainnet test data, an
interrupted write recovered to exactly the rows of an uninterrupted run across
14 tables. Other ingestion fixes: blocks below `--start-block` are no longer
written (#466), bounded runs must prove their stop block (#466), EndpointInfo
failures stop start-up instead of changing the output path (#467), fatal gRPC
errors stop instead of retrying forever (#472), shutdown is prompt (#473) and
invalid timestamps are errors (#476).

### S3

- Every S3 write needs an explicit `s3://bucket/prefix`, and `.env` is never read
  from a parent directory (#617). A run in a checkout below a production `.env`
  once wrote to a production bucket during the audit.
- Mutating commands hold a persistent, conditional bucket-wide owner, and remote
  data mutations make exactly one attempt; an uncertain result keeps ownership
  for explicit recovery instead of being retried blindly (#468).
- Ingestion uploads spool each encoded part to disk and stream one conditional
  PUT with explicit deadlines, instead of buffering it in memory behind a
  30-second request timeout (#520).
- An explicit `s3://` cursor uses its own bucket (#470).

### Maintenance

fireparq has no maintenance commands in v1.0.0 (#643). Compaction, VACUUM and
checkpoints of the Delta tables are an off-the-shelf `deltalake` CronJob beside
the writer ([design §9](../design/delta-lake.md#9-maintenance-cronjob)):
`scripts/delta_maintenance.py` is the reference job, CI runs it over and over
beside a real `build`, and `deploy/examples/` has its CronJobs. A bad dataset
is rebuilt into a new root. The job does not take fireparq's
dataset owner, which guards only fireparq's own writer and state (#636). `merge`, `truncate` and `rollup` are
removed: the audit had made `merge` crash-safe (#480) and schema-strict (#479),
`truncate` confirmation-gated (#481) and `rollup` lossless (#478, #522) first.
`verify` is removed too and returns over Delta snapshots in #666, starting from
the audit's `merkle_v2` work (#487–#490, #521).

### CLI

- `--env-file`, `--cursor none`, `--exclude-failed-transactions`,
  `--flush-memory-bytes`, the flush concurrency options, `--compression
  zstd:<level>`, gRPC receive options, `--metrics-stale-after-secs`, the
  `{chain}` placeholder in `--output` and the `recovery` subcommands are new.
- `merge`, `truncate`, `verify` and `scan` are removed (#643).
- `validate` reads the active files of a pinned Delta snapshot, and `inspect`
  one file (#643).
- The `partitions` subcommands, `_fireparq/partitions.parquet` and
  `--cursor-template` are removed (#653).
- `--output` is the dataset root, used as given (#654).
- Zero consistently means "disabled" for flush thresholds and timeouts, and
  values that crashed are rejected (#471).
- `--final-blocks-only=false` enables append-only non-final output (#474).
- The built-in network registry is regenerated and checked weekly (#535).
- Startup logs name the loaded env file, the resolved write destinations and the
  selected credential variables, never secret values.

### Metrics

Counter names have a single `_total` suffix, `files_written_total` no longer has
an unbounded `partition` label, and gauges that were misleading or always zero
are gone (#475). `/ready` reflects whether the stream is actually delivering
messages. New counters cover fatal gRPC errors, cursor save failures and blocks
skipped below the start block. Two gauges report what a `build` start listed,
which is nothing on a resume (#655). Per table, `build` exports its Delta log's
tail since the last checkpoint (`firehose_parquet_delta_log_tail_commits`, for
alerting when the maintenance job stops), its commit durations and its
retried lost conditional puts (#643).

### Security

- **Credential scoping (#562).** Firehose credentials are sent only to the
  provider they belong to; previously a Pinax key was sent to StreamingFast
  endpoints behind the moved aliases.
- **No writes through parent `.env` files (#617)**; see S3 above.
- **Dependency advisories.** Compatible dependency updates and the Arrow/Parquet
  60 upgrade resolve RUSTSEC-2026-0009, -0037, -0041, -0049, -0097, -0098,
  -0099, -0104, -0185, -0190, -0258 and -0285, and remove the vulnerable Thrift
  dependency (GHSA-2f9f-gq7v-9h6m) (#567, #568; PRs #569, #577, #615). Parquet
  60 also bounds allocations from malformed footer list lengths.
- **cargo-deny in CI.** A pinned, checksum-verified cargo-deny runs
  `cargo deny --locked check advisories` on every push and pull request, and on
  its own every Monday at 05:41 UTC (`.github/workflows/advisories.yml`, check
  name `Dependency advisories / cargo deny check advisories`). Every RustSec
  vulnerability fails the job; unsound and unmaintained advisories fail for
  direct dependencies. Ignored advisories need a recorded reason in `deny.toml`.

## Schema changes by chain

These tables compare the schemas of `v0.7.2` and `v1.0.0`, rendered with each
chain's default encoding (EVM, Beacon, Cosmos and Bitcoin `hex`; Antelope
`hex_no_prefix`; Solana and NEAR `base58`; Tron `tron_base58`), with all
optional tables enabled and without `fork_step` or `stream_ordinal`. `v0.7.2`
columns are named by their Arrow type, `v1.0.0` columns by the Delta type the
files store (#643); the first list below gives the mapping. The complete
current schemas, with every column's Delta type and nullability and each
chain's mapping from the mapper's Arrow types, are in
[`docs/schemas/`](../schemas/README.md).

Changes that apply to every chain:

- The canonical `timestamp` column is a UTC timestamp with millisecond values
  (was `Timestamp(Second, UTC)`) on every table (#491). The files store it as
  Delta `timestamp`, `TIMESTAMP(MICROS, UTC)` (#643).
- Every table is written as `<table>/date=YYYY-MM-DD/part-*.parquet` (#652,
  superseding the `day=DD` directories of #493). `date` is the partition
  column: the files do not contain it (#643).
- Every column has a Delta type (#643): `UInt64` becomes a checked `long`, or
  `decimal(20,0)` for the columns each chain lists; `UInt32` and `UInt16`
  become `long`, `UInt8` becomes `short`, `Int64` stays `long`, `Utf8` is
  `string`, `Binary` is `binary`, `Boolean` is `boolean`, and enum columns
  (built as `Dictionary(Int32, Utf8)`) are `string`. Lists become `array<T>`
  and structs `struct<...>`, element-wise.
- Non-final streams (`--final-blocks-only=false`) add `stream_ordinal`
  (`long`, not null) directly after `fork_step` on every table (#648).
  Final-only schemas are unchanged by it.
- Columns are only removed through the renames listed below; nothing else was
  dropped. Most new columns are appended after the existing ones; where they
  are inserted in the middle of a table, the chain section says so. Readers that
  access columns by position must be updated.
- Schemas that differ only in added columns can be read together with
  `union_by_name`.

## Detailed changelog

Each entry links its issue and pull request(s). The implementation record of
each issue is in [`docs/audit/`](../audit/README.md).

### Breaking changes

#### Ingestion and dataset state

- **All-table ingestion transactions and output authority (#468; PRs #591,
  #600, #619).** `build` journals each complete mapper flush as one transaction
  across all tables and recovers it before opening the Blocks stream. Parts use
  deterministic `part-v1-<stream>-<first>-<last>-<transaction>-<index>.parquet`
  names, so a replayed window republishes the same names instead of adding
  duplicates, and parts of an interrupted transaction are rolled back before
  replay or verified and rolled forward after commit. Output authority under
  `<dataset root>/.fireparq-ingest/` selects the exact accepted cursor, including
  filtered zero-row events and timestamp-routing provenance;
  `_fireparq/cursor.parquet` is an optional mirror whose deletion cannot rewind
  output. The chain, mapper and
  schema digests, encoding, effective feature flags, partition policy, storage
  and mirror binding are immutable for a dataset. Flush thresholds and
  compression stay tunable. A new dataset needs an empty root and an absent
  mirror; existing random-name output and legacy cursors are refused rather
  than adopted. Unknown custom chain metadata needs an explicit `--block-type`
  before recovery. An ordinary error removes the failed transaction's hidden
  `.fireparq-txn-*.tmp` staging files and keeps its journal; after a kill, the
  next `build` or `recovery recover` removes them. Readers of the Delta tables
  see only committed parts, but no atomic multi-table snapshot (see
  Known limitations).
- **`--cursor-override` is refused by a real `build`, and `--cursor none` creates
  a dataset without a mirror (#468, PR #619).** `--cursor-override` cannot bypass
  protected state and is rejected even at a new root (it remains available to a
  read-only `--dry-run`). `--cursor none` (case-insensitive) keeps mandatory
  authority without a mirror; the choice is bound to the dataset, and later
  runs must repeat it.
- **Ownership for every mutating command (#468 prerequisite, PR #591).** `build`
  and `recovery` coordinate ownership of their output and cursor locations. Local mutation needs
  supported macOS/Linux directory inode locking and readable ancestry; nested
  symlinks inside guarded trees are refused. S3 mutation holds a persistent
  bucket-wide owner and requires conditional create/update support, usable
  object versions and access to `.fireparq-owner-v1.json` and
  `.fireparq-owner-probes-v1/`. The owner covers the whole bucket: a second
  mutating command on any prefix of it fails immediately, and there is no
  expiry, automatic takeover or best-effort fallback for stores without
  conditional writes. Remote data writes, deletes and cursor saves make one
  attempt with transport retries disabled. A failed `build` releases the owner
  when every request it sent had a definite outcome (#640); after an ambiguous
  request, and after any error of `recovery`, the owner is kept
  until `fireparq recovery release` frees it after provider-confirmed quiescence
  (see Deployment notes).
- **Bounded runs must prove their stop block (#466, PRs #544, #600).** A run with
  `--stop-block` exits 0 only after block `stop_block - 1` was received and
  committed. A stream that ends early is resumed once from authority; if the
  server has no more blocks, the committed prefix is kept and the command exits
  non-zero on every chain, including chains with skipped slots or heights
  (Solana, NEAR, Beacon), because a sparse or empty tail cannot prove the bound.
  Choose a stop bound that ends at an observed block. `--dry-run` applies the
  same rule. An already proven bound makes no Blocks request.
- **Start-up requires EndpointInfo (#467, PR #570).** Ingestion stops before
  resolving output and cursor paths if endpoint metadata cannot be read. Info is
  tried up to three times with bounded back-off; authentication errors, an
  unsupported Info RPC and empty chain names fail promptly. Explicit network,
  block type or start bounds do not bypass this, so a transient failure can no
  longer change the output prefix or resume point.
- **Invalid timestamps and missing stream metadata are errors (#476, PR #584).**
  Malformed timestamp seconds or nanos, and values outside years -9999 to 9999,
  fail before any row or partition file is written instead of falling back to
  1970, saturating or panicking. Streamed blocks must carry a metadata object.
- **Local publication requires durable filesystem operations (#578, PR #580).**
  Local parts become visible at their final name only after the footer is
  complete and the file is synced; publication is atomic and never overwrites a
  destination. Filesystems must support atomic hard links and file/directory
  sync, and directory sync failures are fatal.
- **EVM includes failed transactions by default (#494, PR #547).** A failed EVM
  transaction still pays gas and fees and increments the sender's nonce. `build`
  now writes it with all of its calls and gas changes, and only the state changes
  that persist: root-call `balance_changes` with reason `GAS_BUY`, `GAS_REFUND`,
  `REWARD_TRANSACTION_FEE` or `INCREASE_MINT`; the sender's nonce increment plus
  one `nonce_changes` row per accepted EIP-7702 authorization; at most one
  `code_changes` row per accepted authorization; no storage changes, account
  creations or other balance changes. `--exclude-failed-transactions`
  (`EXCLUDE_FAILED_TRANSACTIONS`) restores the previous EVM output and wins over
  `--include-failed-transactions` on every chain that filters failed
  transactions;
  `--include-failed-transactions` is deprecated for EVM, has no effect there and
  logs a warning. A protected EVM output created with
  `--exclude-failed-transactions` keeps excluding failed transactions when
  resumed (with a warning unless the flag is repeated); switching needs a new
  root. EVM outputs built with `--include-failed-transactions` before this
  release contain rolled-back transfers and storage writes; rebuild them to
  reconcile state.
- **Tron excludes failed smart-contract calls, and Antelope keeps `onerror`
  handlers and scheduled transactions (#550, PR #622).** Tron's filter used the
  Firehose wrapper `result`, which java-tron sets to success for every included
  transaction, so reverted and out-of-energy calls were always written. A Tron
  transaction now fails when `TransactionInfo.result` is `FAILED` or its receipt
  result is neither `DEFAULT` nor `SUCCESS`, and failed transactions are excluded
  unless `--include-failed-transactions` is set. Antelope kept only `EXECUTED`
  traces; a trace now succeeds when it has no exception and its status is
  `EXECUTED`, `SOFTFAIL` or `DELAYED`, so `onerror` handlers and scheduled
  transactions are kept, while the failed deferred trace beside an `onerror`
  handler, `HARDFAIL` and `EXPIRED` stay excluded. NEAR receipt rows are always
  written and now carry `receipt_status`.
- **Solana vote filtering keeps administrative activity (#501, PR #586).** The
  vote table and `--without-votes` apply only to legacy single-instruction votes
  with fully decoded, recognized payloads. Withdraw, Authorize, vote-account
  creation, mixed instructions, unused Vote program keys, versioned transactions
  and unknown payloads keep their ordinary detail rows. Schemas are unchanged,
  but affected rows change.
- **`--flush-bytes` is an adaptive compressed-file target (#515, PR #605).**
  `build --flush-bytes` targets the largest compressed file of a flush, using
  feedback from committed transactions, instead of the raw in-memory size of the
  largest table. `build` has a 32 MiB default (the library
  `Config` used 128 MiB). `build` also flushes when the sum of
  mapper estimates reaches `--flush-memory-bytes` (default 256 MiB), which stays
  active with `--flush-bytes 0`; it is not an RSS cap and one block can overshoot.
- **Parquet layout and explicit Zstandard levels (#519, PR #608).** Ingestion
  parts get bounded Bloom filters on lookup columns, a 65,536-row group
  maximum and, for complete ingestion parts, block-number sort metadata. Arrow
  schemas, values and row order are unchanged. `--compression zstd:<level>`
  selects a level; plain `zstd` stays level 3. Non-default levels are bound into
  pending transaction identities, so finish any recovery before downgrading.

#### Output layout and schemas

- **Every table is partitioned by a single `date=YYYY-MM-DD` key (#652, PR #660).**
  `build` writes `<table>/date=YYYY-MM-DD/part-*.parquet` and nothing else: the
  `--partition` modes (`none`, `block_range`, `date`, `hour`, `minute`,
  `second`), `--block-range-size`, `PARTITION` and `BLOCK_RANGE_SIZE` are
  removed, and so is `rollup`, whose only job was coarsening partitions. The key
  and the mapper's `date` come from the same checked block time, and a flush
  whose row `date` disagrees with its directory, or that has no routing time,
  is refused; since #643 the files no longer store `date` (see the next
  entry). DuckDB and Polars read it as the `date` column from the Delta log
  (#643; `delta_scan`, `scan_delta`) and prune by it; CI reads every table
  with DuckDB 1.5.5 and Polars 1.44.2 (`blocks/tests/engine_compat.rs`). JVM
  engines are not a target. The semantic mapper epoch became `fireparq-mapping-v2` (now `v3`,
  #643), so a protected
  dataset from a pre-release build (`year=/month=/day=` or another layout) is
  refused before any Blocks request instead of being resumed into a mixed
  layout; a root holding data of any layout without authority is refused as
  before. There is no compatibility with the older keys.
  The cursor mirror's footer keeps `firehose-parquet.partition=date`, no file
  records `block_range_size` any more, and `firehose_parquet_info` drops its
  `partition` label.
- **Parts are Delta data files: Delta column types, microsecond timestamps and
  `date` as the partition column only (#643, L2; PR #669).** Delta has no unsigned,
  dictionary or millisecond types, so every flush maps the mapper's Arrow types
  once, before the transaction journals anything
  (`firehose_parquet::delta::types`): `UInt64` becomes a checked `long`, and a
  value above 9,223,372,036,854,775,807 refuses the whole flush with the table,
  column and value named, instead of wrapping or becoming null; the `UInt64`
  columns that hold currency amounts or values a sender or signer chooses
  without a range check become `decimal(20,0)`, listed per chain in
  `ChainProfile::decimal_columns` (EVM `blocks.nonce`,
  `set_code_authorizations.nonce`, `withdrawals.amount_gwei`; Solana `fee`,
  `pre_balances`, `post_balances`, `rewards.post_balance`; Beacon `amount`
  columns and the slashing evidence slots and epochs; Antelope
  `actions.error_code`; Cosmos `timeout_height`, `fee_gas_limit`; Bitcoin
  satoshis stay `long`). `UInt32` and `UInt16` become `long`, `UInt8` becomes
  `short`, lists element-wise, and enum columns become plain `string` (Parquet
  still dictionary-encodes their pages). `timestamp` columns keep their
  millisecond values and are stored as `TIMESTAMP(MICROS, UTC)`, which Polars
  requires under a Delta `timestamp` column. `date` leaves the files: its value
  is the `date=YYYY-MM-DD` directory and the Delta `partitionValues.date`, and
  a Solana row without `block_time` now gets its routing
  day as `date` instead of null (its `timestamp` stays null). DuckDB now reads
  `BIGINT` (was `UBIGINT` or `UINTEGER`), `SMALLINT[]` (was `UTINYINT[]`) and
  `DECIMAL(20,0)` (was `UBIGINT`); Polars reads `Int64` (was `UInt64` or
  `UInt32`), `List(Int16)` (was `List(UInt8)`), `Decimal(precision=20,
  scale=0)`, `String` (was `Categorical`) and `Datetime('us', 'UTC')` (was
  `Datetime('ms', 'UTC')`). Read `date` through the Delta log (`delta_scan`,
  `scan_delta`); the files do not store it. The semantic mapper epoch is now
  `fireparq-mapping-v3`, so a protected root written with `v2` types is refused
  before any Blocks request; build into a new root.
  [`docs/schemas/`](../schemas/README.md) lists every column's Delta type and
  ends each chain with its mapping, and the record is
  [643-l2-delta-types.md](../audit/643-l2-delta-types.md).
- **Every `build` writes Delta tables (#643, L3; PR #671).** Each mapper table
  is a Delta table at `<root>/<table>/`, created at the first start (also for
  tables that never get rows) with reader 1 / writer 2 and no table features,
  `date` as the only partition column, `delta.appendOnly`, 7-day log and
  deleted-file retention, statistics on `block_num` and `timestamp`, and the
  `fireparq.descriptor`, `fireparq.chain` and `fireparq.blockType` properties
  that bind it to its stream. A resume validates every table against its
  stream (properties, identity, protocol, partition and schema), and once the
  stream has committed, a table without a log is refused. Each transaction's
  parts are its data files, unchanged: after the journal is Committed, every
  table with a part gets one commit (the part's `add`, with its size, partition
  value, modification time and `numRecords`/min/max/null-count statistics from
  the journal, and `txn {appId: fireparq:<descriptor>, version: last
  ordinal}`), the other tables first and `blocks` last, and only then does
  authority advance. A block visible in `blocks` therefore has its rows in every
  table; filter child tables by `block_num <= (SELECT max(block_num) FROM
  blocks)` for a consistent cut. The commits are blind appends, so the
  `deltalake` maintenance job can OPTIMIZE and VACUUM beside the writer, and a
  second writer with the same `appId` fails instead of adding rows twice. On S3
  the log goes through its own single-attempt client with conditional puts
  (`If-None-Match: *`). Pending journals of earlier
  development builds (without the new receipt fields) are refused. delta-rs's
  own `info` logs are lowered to `warn` unless `--log-level` names them.
  Recovery of a transaction interrupted between Committed and the authority
  advance is the next entry (L4). Record:
  [643-l3-delta-commits.md](../audit/643-l3-delta-commits.md).
- **Recovery rolls an interrupted transaction forward into the Delta tables
  (#643, L4; PR #675).** Every start, of `build` and of `recovery recover`,
  first reads each table's `txn` and refuses a log ahead of authority (an
  authority restored from an older copy, or another writer using the
  stream's `appId`) before it changes anything. A transaction that crashed
  after its journal was Committed is then committed to exactly the tables
  whose `txn` lacks it, `blocks` last, after only their parts were verified
  against the journal, and authority advances; each table holds it once, and
  a roll-forward that is itself interrupted is finished the same way. Tables
  that already hold it, and every table once authority does, are not read
  again, so a restart works after the maintenance job compacted and vacuumed
  their parts. If a part a table does not reference yet is gone (only a full
  VACUUM with a retention shorter than the outage deletes one), recovery
  stops with a message that names the part, how long the transaction was
  pending and the tables that hold it, and keeps the journal; rebuild into a
  new root. A Delta commit whose outcome is unknown (a timeout, a lost
  response) no longer keeps the S3 bucket owner: the build fails, releases
  it, and the next start reads the table's `txn` and commits only what did
  not land. A start interrupted while it created the tables creates the rest.
  Record: [643-l4-delta-recovery.md](../audit/643-l4-delta-recovery.md).
- **The dataset owner no longer blocks Delta maintenance (#636, PR #675).**
  The owner record guards fireparq's writer and its own state
  (`.fireparq-ingest/`, `_fireparq/`, its uncommitted parts) and not the Delta
  tables, which the `deltalake` maintenance job compacts, vacuums and
  checkpoints through their logs beside a running `build`. The README
  ownership section gives the bucket policy for the writer and the
  maintenance user. Record: [636-delta-ownership.md](../audit/636-delta-ownership.md).
- **fireparq's artifacts live in `<dataset root>/_fireparq/` (#647, PR #650).** The
  default cursor mirror is `_fireparq/cursor.parquet` (`--cursor`, relative to
  the dataset root). This holds at every dataset root, including an S3 bucket root. The
  root then holds only table directories, `_fireparq/` and dot-prefixed control
  state (`.fireparq-ingest/`, `.fireparq-owner-v1.json`,
  `.fireparq-owner-probes-v1/`), none of which is a table: readers open each
  table through its own log, and no command or reader walks a table's files
  (#643). The mirror location
  stays bound at creation: a dataset created with the old default refuses the
  new one and is resumed with `--cursor cursor.parquet`. Local writes create
  `_fireparq/` durably (default permissions; the mirror file stays `0600`).

- **Canonical `timestamp` keeps millisecond block times on every table (#491,
  PR #539).** It was `Timestamp(Second, UTC)`, which Parquet has no logical type
  for, so DuckDB, Spark, Trino and ClickHouse read it as `BIGINT`. It is now a
  real Parquet timestamp and keeps the milliseconds of the Firehose block time
  (Antelope blocks show `.500`); since #643 the files store it as a Delta
  `timestamp`, `TIMESTAMP(MICROS, isAdjustedToUTC=true)`. Antelope
  `actions.block_time` uses the same type. `date`, the `date=` partition
  and the cursor's `last_timestamp` are still derived from the whole-second
  block time. A Solana row without `block_time` has a null `timestamp` and the
  `date` of its routing day.
- **The day-of-month `date=DD` key is gone (#493, PR #543; superseded by
  #652).** v0.7.x wrote the day of the month as `date=DD`, which collided with
  the `date` column in Hive-aware readers (DuckDB read `date` as a day number;
  Polars failed). #493 first renamed it to `day=DD`; #652 then replaced the
  `year=/month=/day=` keys with the single `date=YYYY-MM-DD` key above.
- **Unique column names on every table (#492, PR #534).** Tron `transactions`
  had two `timestamp` columns; the transaction's own times are now
  `tx_timestamp_ms` and `expiration_ms` (raw `Int64` milliseconds, set by the
  sender and not validated on chain). A contract test checks every table of every
  chain for unique names and a Parquet round trip. NEAR `state_changes` now
  writes `block_id` / `parent_id` in base58 like the other NEAR tables (it used
  `0x` hex, so it could not be joined to `blocks`).
- **Per-chain schema changes.** Every chain gains, renames or retypes columns;
  see [Schema changes by chain](#schema-changes-by-chain): EVM (#494, #495,
  #496, #497), Solana (#500, #502, #503, #550), Beacon (#504, #505), NEAR (#506,
  #507, #550), Antelope (#508, #550), Tron (#492, #509, #550), Cosmos (#510) and
  Bitcoin (#511).

#### S3, credentials and configuration

- **S3 writes need an explicit URI; `.env` is read from the working directory
  only (#617, PR #623).** `fireparq` used to load `.env` from the current
  directory or any parent directory, and `build` expanded a relative
  `--output` (including the default `.`) into `s3://$S3_BUCKET/<path>`,
  so a run started below a directory holding a production `.env` could write to
  the production bucket. Now `.env` is loaded from the working directory only,
  or exactly the file given with `--env-file` / `FIREPARQ_ENV_FILE`; parent
  directories are never searched; a malformed file is an error; and startup
  names the loaded file and the variables it supplied, never their values. With
  `--s3-bucket` / `S3_BUCKET` set, `build` rejects a relative output before
  contacting the endpoint; the bucket option only checks the bucket of an
  explicit S3 output. `build` logs its resolved output
  and mirror destinations before the first write.
- **S3 cursors use their exact bucket (#470, PR #573).** An explicit
  `s3://bucket/key` cursor selects its own bucket and key; relative cursor paths
  inherit the output bucket and prefix. An explicit S3 output must agree with `--s3-bucket` / `S3_BUCKET`, a
  bucket-bound endpoint rejects a different cursor bucket, and an S3 cursor needs
  complete explicit AWS credentials even with local output.
- **Native S3 ingestion uploads (#520, PR #613).** Authenticated protected
  `build` encodes each part to a private disk spool, streams one conditional
  PUT, and verifies the object through a second spool before committing.
  Native ingestion requires an HTTPS endpoint, caps each encoded part at
  5,000,000,000 bytes and rejects serialized footers above 32 MiB, even during
  resume verification; an oversized part fails with its journal retained instead
  of falling back to multipart. Upload and readback each have a 15-minute
  deadline with a 10-second connect timeout. Allow temporary disk for about two
  encoded parts.
- **Firehose credentials are scoped to the destination provider (#562, PRs #566,
  #615).** Credentials are chosen from the resolved host after endpoint
  overrides. The HTTPS hosts of built-in Pinax aliases use `PINAX_API_KEY` /
  `PINAX_API_TOKEN`,
  with `SUBSTREAMS_API_KEY` / `SUBSTREAMS_API_TOKEN` as legacy Pinax-only
  fallbacks; the hosts of built-in StreamingFast aliases use `STREAMINGFAST_API_KEY` /
  `STREAMINGFAST_API_TOKEN`. Automatic selection requires port 443; unknown hosts,
  other ports, URLs with user info and plaintext endpoints get no ambient
  credential. For custom
  endpoints, choose variables with `--api-key-envvar` / `--api-token-envvar`
  (`API_KEY_ENVVAR` / `API_TOKEN_ENVVAR`); an unset or blank selected variable
  omits its header, and startup warns whenever an explicitly selected credential
  is sent to a non-Pinax host. Logs show host and variable names, never values.
- **Built-in `--network` aliases (#535, PR #541).** The registry is regenerated
  from The Graph networks registry (v0.8.4). Thirteen aliases are removed
  (`bnb-op`, `bnb-svm`, `fantom`, `fuse`, `gnosis-chiado-cl`, `mode-mainnet`,
  `moonbeam`, `moonriver`, `ronin`, `scroll`, `scroll-sepolia`, `telos`,
  `telos-testnet`) and rejected during argument parsing. `near-mainnet`,
  `near-testnet`, `tron` and `tron-evm` moved to StreamingFast endpoints and need
  a StreamingFast credential; `arc`, `megaeth`, `robinhood`, `tempo` and
  `xlayer-mainnet` are new.

#### Maintenance

- **Reference Delta maintenance job (#643, L9; PR #673).** `scripts/delta_maintenance.py`
  runs `deltalake` 1.6.6 (hash-pinned in
  `scripts/delta_maintenance.requirements.txt`; the script refuses another
  version) over the tables of one dataset root (`LAKE_ROOT`, or `LAKE_BUCKET`
  for a bucket-root lake, and `LAKE_TABLES`). For each table: OPTIMIZE of every
  closed `date` with more than one file (a date is closed once `blocks` holds
  a later one; `OPTIMIZE_DATES=all` also compacts the newest), a lite VACUUM
  (tombstoned files only, never an uncommitted part), or a full VACUUM with
  `FULL_VACUUM=1`, which it refuses below 168 h, then a checkpoint, which it
  writes only after a successful VACUUM (a checkpoint first would orphan the
  files of expired tombstones: measured), and log cleanup. OPTIMIZE and VACUUM
  write no checkpoint of their own. Settings come from the environment
  (`S3_ENDPOINT`, `AWS_*`, `VACUUM_RETENTION_HOURS`, `OPTIMIZE_TARGET_SIZE`,
  `OPTIMIZE_ZSTD_LEVEL`, `OPTIMIZE_MAX_CONCURRENT_TASKS`, `DRY_RUN`), log
  commits use conditional puts, credentials are never printed, and each run
  prints JSON lines and exits 0, 1 (a table failed) or 2 (configuration).
  Every step is idempotent. `deploy/examples/delta-maintenance-cronjob.yaml`
  runs it hourly and a full VACUUM weekly, as a non-root user with a read-only
  root filesystem and a `/tmp` `emptyDir`. `blocks/tests/delta_maintenance.rs`
  runs it over and over beside a real `fireparq build` (local disk and a
  loopback S3 endpoint, a clean restart over the compacted tables, the open
  date compacted too): no writer failure, no conflict, exact rows through
  `delta_scan` and `scan_delta`, `txn` versions intact, one file per closed
  date. Record: [643-l8-l9-engines-maintenance.md](../audit/643-l8-l9-engines-maintenance.md).
- **`rollup` is removed (#652, PR #660).** It rolled `minute`/`hour` partitions up into
  `hour`/`date`. With a single `date` partition key there is nothing to roll
  up, so the subcommand, its `_fireparq_rollup.json` journal, the
  `firehose-parquet.rollup_copy` footer marker and `FIREPARQ_TEST_ROLLUP_CRASH_AT`
  are gone. The `deltalake` maintenance CronJob compacts closed dates (#643).
  (The audit had fixed its re-run data loss and memory use first: #478, #522.)

  `merge` (replaced by the `deltalake` maintenance CronJob), `truncate` (no

  There is no compatibility path: the subcommands and all their flags are

  `{"recovered_protected_roots": N}` only. `merkle_roots.parquet` and

  command reads `_fireparq/` as table data, so an old registry there is left
  alone. Drop
  `merge`, `truncate` and `verify` jobs. See
  [643-l5a-removals.md](../audit/643-l5a-removals.md).

- **The plain-Parquet output and its readers, and `scan`, are removed (#643,
  L5b/L7; PR #672).** Every file `build` writes is a part of the protected transaction,
  committed to its table's Delta log; the unprotected writer of standalone
  table files (`writer::OutputWriter` and `ParquetTableWriter`, local and S3)
  is gone, and the partition routing and part encoding it shared with the
  transaction are plain functions (`writer::partition_suffix`,
  `writer::encode_parquet`). No command reads a table by walking its
  directory: a walk would read the files that OPTIMIZE replaced but VACUUM has
  not deleted yet, their rows twice, and the log's `*.checkpoint.parquet`
  files. `scan` (`--limit`, `--offset`, `--order`, `--schema-only`,
  `--vertical`, `--json`) is an unknown subcommand: DuckDB `delta_scan` and
  Polars `scan_delta` read rows and schemas, and a table's files, rows
  (`numRecords`), bytes and days come from its log alone (the README's
  `deltalake` summary). `inspect` reads one file (a data file, a checkpoint,
  the mirror) and refuses a directory. The walker that `recovery` and
  `build`'s overlap check use skips every `_delta_log/`. See
  [643-l5b-l7-readers.md](../audit/643-l5b-l7-readers.md).

- **Removed: `partitions` subcommands and `partitions.parquet` (#653), replaced
  by Delta log metadata.** `partitions build`, `ls`, `validate`, `resolve` and
  `shard`, their flags and `_fireparq/partitions.parquet` are gone, with no
  compatibility path. Delta Lake output (#643) records the files of each `date`
  partition and their `block_num` statistics in its log, so readers get
  partition pruning and block-range lookups without a custom index, and no
  command needs a day-boundary lookup. The block range of a day is a query over
  the table:

  ```sql
  -- Answered from the Delta log's statistics (#643)
  SELECT min(block_num), max(block_num)
  FROM delta_scan('<root>/blocks')
  WHERE date = DATE '2026-09-25';
  ```

  The finalized-coverage probing that existed only to build the index is
  removed too (finality proofs, finalized metadata traversal and single-block
  Fetch probes); `build` uses EndpointInfo and the Stream RPC only.
  `partitions.parquet` is no longer a reserved artifact name, and `build` no
  longer accepts a new root that holds only a `_fireparq/partitions.parquet`: a
  new root must be empty, and a leftover index is refused like any other file
  (the #650 refusal of a legacy root index is gone with it). Delete the file or
  use a new root. No command reads `_fireparq/` as table data, so a leftover
  `_fireparq/partitions.parquet` is left alone. Drop `partitions` jobs, and
  replace `partitions resolve` plus `build --start-block/--stop-block` with the
  query above.
- **`--cursor-template` / `CURSOR_TEMPLATE` is removed (#653).** `build`
  supplied no template variable, not even `{chain}`, so a template was a literal
  path, and the partition variables (`{partition_type}`, `{partition_value}`,
  `{partition_from}`, `{partition_to}`) had no producer. Pass the path with
  `--cursor` / `CURSOR`: relative to the dataset root, absolute, or `s3://`.
  `{chain}` stays in `--output`.

  non-final runs warn that completion does not establish tail finality.
- **Dedup-safe non-final output: `stream_ordinal` (#648, PR #649).** Every
  row of a non-final stream carries `stream_ordinal` (`long`), directly after
  `fork_step` on every table of every chain: the accepted-event ordinal of the
  NEW, UNDO or FINAL envelope that produced it. It is the same for every row of
  one envelope in every table, strictly increasing in delivery order, and
  durable: it is assigned by the protected ingestion session and continues from
  the output authority across reconnects and restarts (each part's name records
  its ordinal window). `build` refuses a non-final flush whose rows fall outside
  the accepted prefix it commits. Final-only schemas are byte-identical.
- **Canonical live view (#648, PR #649; #643).** The README replaces the
  finalized-intersection query with a tested DuckDB view of the chain head over
  the non-final Delta tables (`delta_scan`): for each `block_num` the latest
  event by `stream_ordinal` decides (NEW or FINAL of X: X is canonical; UNDO: no
  block), and child rows are kept only when their `(block_num, block_id,
  stream_ordinal)` matches that event, so repeated deliveries such as NEW(A),
  UNDO(A), NEW(A) keep one copy. CI runs the exact README SQL against real
  mock-stream output with a pinned DuckDB CLI and its `delta` extension.
  Non-final output is a CLI capability; the two-bucket live + final deployment
  written up during development is gone ([Removed](#removed)).
- **`fireparq recovery` (#468).** `recovery status` reads ownership and control
  summaries, `recovery recover` performs offline owned recovery, and
  `recovery release` releases a remote owner after provider-confirmed
  quiescence.
- **`--env-file` / `FIREPARQ_ENV_FILE` (#617)**, **`--cursor none` (#468)** and
  **`--exclude-failed-transactions` (#494)**; see above.
- **`--output` is the dataset root; opt into `{chain}` (#654, PR #656).** `build`
  uses `--output` exactly as given: `OUTPUT=s3://ethereum-mainnet`
  puts the tables at `s3://ethereum-mainnet/<table>/...`. The `{chain}`
  placeholder expands to the endpoint's canonical `chain_name` anywhere in a
  local path or an S3 key prefix, for example `--output 's3://datasets/{chain}'`
  (`s3://datasets/mainnet`) or `s3://datasets/v1/{chain}/raw`. `{{` and `}}`
  are literal braces, and an unknown
  variable, an unterminated `{` or an unmatched `}` is refused before the
  endpoint is contacted. The S3 bucket name is literal, so `s3://{chain}/...` is
  refused. A trailing `/` never changes an S3 root (`s3://bucket/` is
  `s3://bucket`). EndpointInfo must still report a nonempty chain name, which
  stays in file metadata and in the protected dataset identity. One resolver
  serves `build`, the cursor mirror, dataset ownership and recovery, and the resolved root is logged before any write. The root is bound
  at creation: a later run whose `--output` resolves inside or above the
  dataset, such as `s3://b/{chain}` for a dataset created at `s3://b` or the
  reverse, is refused before any Blocks request (`selected ingestion output
  overlaps another protected root`). See the deployment note above and
  [the implementation record](../audit/654-output-template.md).
- **Receive transport options (#517, PR #602).** `build` exposes
  `--grpc-window-bytes` (default 16 MiB), `--grpc-adaptive-window` and
  `--grpc-max-message-bytes` (default 128 MiB). Replies may use zstd as well as
  gzip; an oversized compressed response stops without retrying the same payload.
- **`--compression zstd:<level>` (#519)** and **`--flush-memory-bytes` (#515)**.
- **Adaptive flush interval (#659, PR #664).** `--flush-interval-secs` applies only
  while `build` follows the chain head. While it catches up (a first start, a
  restart after an outage, or a `--stop-block` backfill far behind the head),
  the interval is suspended and the size triggers (`--flush-bytes`,
  `--flush-memory-bytes`), `--flush-rows`, `--flush-blocks`, day boundaries and
  the end of the stream flush, so files reach the 32 MiB target instead of
  holding an interval's worth of history. There is no new flag: `build`
  compares block time with the wall clock over samples of at least 5 seconds.
  It is catching up after three samples covering 30 seconds at more than 2×,
  and caught up after 20 seconds at no more than 1.25× (its own commits
  excluded) or 60 seconds without a block timestamp. This works on final-only
  streams, which stay at the finality lag even at the head, and on Ethereum or
  Base finality bursts; missing or backward timestamps never count as catching
  up. Each switch is logged once with `block_time_ratio` and `blocks_per_sec`,
  the new `firehose_parquet_catching_up` gauge is 1 while catching up, and
  `firehose_parquet_flushes_total` gains a `pace` label
  (`catching_up`/`caught_up`). See
  [the README](../../README.md#flush-interval-and-catch-up) and
  [the implementation record](../audit/659-adaptive-flush.md).
- **Readiness and new metrics (#466, #469, #472, #475).** `/ready`,
  `--metrics-stale-after-secs`, message-freshness and block-age gauges, separate
  mapper/writer/bootstrap buffer gauges,
  `firehose_parquet_blocks_skipped_below_start_total`,
  `firehose_parquet_cursor_save_failures_total`,
  `firehose_parquet_cursor_last_success_timestamp_seconds` and
  `firehose_parquet_errors_total{kind="grpc_fatal"|"cursor_save"}`.
- **New network aliases (#535):** `arc`, `megaeth`, `robinhood`, `tempo`,
  `xlayer-mainnet`.

### Fixes

#### Ingestion and cursor

- **A failed S3 `build` releases bucket ownership when that is provably safe
  (#468, PR #640).** `build` kept the S3 bucket owner after any error, even when
  nothing had been written (for example a Blocks `Unauthenticated` error or a
  stream failure before the first flush), so every other writing command on the
  bucket failed with `bucket ownership is held` until someone ran `recovery
  release` with provider-quiescence evidence. A failed `build` now releases the
  owner when every request it sent had a definite outcome, including a failed
  transaction left pending (the next `build` rolls it back or completes it
  before streaming). An HTTP 401/403 refusal of a part, control-record or
  cursor-mirror PUT counts as definite. Ownership is still kept after an
  uncertain request, a second shutdown signal or a panic, and the error names
  each kept owner, why it was kept and the exact recovery commands. Other
  mutating commands keep their behavior and log the same guidance. See
  [the exit-path record](../audit/s3-owner-safe-release.md).
- **A failed table write no longer loses rows (#464, PRs #532, #600).** The
  uncommitted window is discarded, authority and cursor do not advance, the
  process exits non-zero, and recovery removes parts the failed transaction had
  published before the window is replayed. Previously the error path flushed the
  other tables and saved the cursor past the lost rows.
- **An unreadable cursor no longer restarts ingestion from scratch (#465, PR
  #538).** A cursor that exists but cannot be loaded fails the run instead of
  re-ingesting from `--start-block` or genesis and overwriting the good cursor.
  With #468, a missing mirror is repaired from authority and an unreadable or
  corrupt mirror fails closed.
- **Local cursor saves are atomic (#465, #468).** The mirror is written to a
  private temporary file, synced, renamed, and its directory ancestry synced; S3
  mirror updates use one conditional write and an exact readback.
- **Failed cursor saves stop `build` (#469, PR #571).** A local mirror save gets
  three attempts with 1 s and 2 s back-off; an S3 update gets one conditional
  attempt. Exhausted or ambiguous saves stop `build` with a non-zero exit. The
  mirror is published after the all-table commit, so a failed save never loses
  rows.
- **The final flush on completion is checkpointed (#572, PR #576).** A completed
  stream could write its last batch and skip the final cursor save.
- **Blocks below `--start-block` are no longer written (#466, PR #544).** When
  the start block is above the last irreversible block, Firehose serves from
  LIB+1; those blocks are now skipped, logged once and counted.
- **Live runs reconnect when the stream closes cleanly (#466).** A clean close
  used to exit 0, so `Restart=on-failure` supervisors never restarted it.
- **Fatal gRPC errors end the run (#472, PR #556).** `Unauthenticated`,
  `PermissionDenied`, `InvalidArgument`, `FailedPrecondition`, `OutOfRange`,
  `Unimplemented` and quota-exhausted `ResourceExhausted` (including statuses
  relayed as `Unknown`) stop with a hint instead of reconnecting forever; other
  `ResourceExhausted` errors are retried. Back-off and the stall timer reset only
  when a stream message arrives, and a run gives up after 30 consecutive failed
  attempts without a message.
- **Shutdown is prompt (#473, PR #579).** SIGINT/SIGTERM interrupt idle waits,
  reconnect back-off, connection attempts and startup checks; a block being
  processed still finishes. A second signal exits immediately with code 130.
- **CLI values that crashed or misbehaved are rejected or consistent (#471, PR
  #553; PR #615).** `--stop-block 0` is rejected, and
  `build` rejects a `--stop-block` at or below the start (it is exclusive). A
  bounded run never sends `stop_block_num = 0`, so `--start-block 0
  --stop-block 1` ingests block 0 and stops. `0` disables `--flush-bytes`,
  `--flush-rows`, `--flush-interval-secs`, `--stream-idle-timeout-secs` and
  `--reconnect-stall-timeout-secs` instead of flushing after every block or
  causing reconnect storms. API keys and tokens are trimmed, and a credential
  that cannot be sent as a header is a startup error instead of a panic.
- **One partition per mapper flush (#477, PR #581).** An unreachable writer path
  that re-split partitions (interpreting millisecond timestamps as seconds) is
  removed; all tables are validated before any publication.
- **Legacy Antelope cursors with `bytes_encoding=auto` validate against
  `hex_no_prefix` (#550, PR #622).**
- **Help text and messages match protected resume (PRs #639, #641).** Root and
  `build` help say a rerun resumes from the `.fireparq-ingest/` authority, with
  `_fireparq/cursor.parquet` only an optional mirror (`--cursor none`), and no longer claim
  that `build` skips missing blocks after probe retries (`build` never
  probes). The startup summary reads `missing_blocks     not probed; the stream
  delivers only produced blocks`. With a bucket option set, the error for the
  default output `.` suggests `--output "$(pwd)"` or `./output` instead of `./.`.

#### Validate

- **`validate` reads a pinned Delta snapshot (#643, L7; PR #672).** It takes a Delta
  table, normally `<root>/blocks` (local, `s3://` or an `S3_BUCKET` key), pins
  its latest version, and reads exactly the active data files that version
  lists, grouped by their `date` partition value from the log; the output
  names the version. An active file that has disappeared (a VACUUM during the
  run) fails the run. It keeps the gap, duplicate, parent-hash and
  timestamp-reversal checks, per partition and across partitions. The
  file-to-file schema comparison, the empty-partition warnings and the ordering
  count are gone: the log holds one schema, which `build` checks at every
  start, and lists no empty partition, and the ordering count could not fire on
  sorted blocks. `block_num` must be a Delta `long` and `timestamp` a
  timestamp (legacy `Int64` epoch seconds are refused).
- **`validate` detects timestamp reversals (#484, PRs #537, #618).** The
  canonical timestamp was downcast to `Int64`, so every value read as 0. Any
  timestamp unit is now read, nulls are compared against the last known value,
  comparisons use milliseconds, and reports print `.mmm`.
- **`recovery` reads `AWS_ENDPOINT_URL_S3` (PR #639).** Its `--aws-endpoint-url`
  read only `AWS_ENDPOINT_URL`, so an environment set up for `build` sent
  `recovery` to AWS instead of the configured S3-compatible endpoint.
  `AWS_ENDPOINT_URL` is still read when neither the flag nor
  `AWS_ENDPOINT_URL_S3` is set; `AWS_ENDPOINT_URL_S3` wins when both are.

### Performance

- **Bounded concurrent table work inside each flush (#516 stage A, PR #629).**
  `build` encodes and publishes one flush's parts concurrently:
  `--flush-encode-concurrency` (default 2), `--flush-publish-concurrency`
  (default 4; for local output also the threads that stage, publish and verify
  files) and `--flush-inflight-bytes` (default 256 MiB of encoded parts, in
  memory or in the native-S3 disk spool; one larger part runs alone with a
  warning). Receipts that are ready together are journaled in one write and each
  is durable before its part publishes; authority and the mirror advance only
  after every part is published and verified; the first error drains started
  work and keeps the journal. Output bytes and names are identical to serial
  work, and `--flush-inflight-bytes 1` makes it strictly serial. The gRPC stream
  still pauses during each flush (stage B, #630).
- **Canonical identity columns are encoded once per block (#512, PR #548)**,
  byte-identically.
- **Hex and base58 columns no longer allocate a string per value (#514, PR
  #563)**, byte-identically.
- **Fixed-size base58 conversion uses safe integer limbs (#565, PR #598).**
  32-byte keys and 64-byte signatures use a stack encoder; other lengths,
  including Tron checksummed addresses, keep `bs58`. Output is unchanged.
- **EVM decimal conversion writes directly into Arrow (#513, PR #596).** Up to
  32 significant bytes use a stack buffer; larger inputs keep an
  arbitrary-length fallback. Values are unchanged.
- **Protobuf byte fields share the owned Firehose payload (#518, PR #606).**
- **Tuned gRPC receive transport (#517, PR #602)**; see New features.
- **Adaptive compressed file targets (#515, PR #605)**; see Breaking changes.
- **Bounded Parquet lookup properties (#519, PR #608)**; see Breaking changes.
- **Native S3 uploads stream from a disk spool (#520, PR #613)**; see Breaking
  changes.
- **Projected dataset validation (#524, PR #599).** `validate` decodes only the
  canonical id/height/time columns and compares cached partition endpoints,
  which also fixes endpoint selection when partitions overlap.
- **Restarts cost the same at any dataset size (#655, PR #668).** Every S3
  `build` start used to list the whole dataset root three times, each capped
  at 60 seconds, so a continuous writer's restarts slowed down and eventually
  failed as its dataset grew; a local start walked the tree four times. A
  resume now reads only its control records: the owner record,
  `.fireparq-ingest/` and the `_fireparq/cursor.parquet` mirror, plus one LIST
  of a control prefix per directory above the dataset (none for a dataset at
  the bucket root). It lists and walks no data. Nested and enclosing datasets
  are still refused: a new dataset checks every directory above and below it
  while its root is empty, and a resume checks the directories above it, so a
  dataset created later inside another is refused by its own check. Listings
  that remain have a 60-second
  timeout per request, no overall deadline and progress logs. The new
  `firehose_parquet_startup_list_requests` and
  `firehose_parquet_startup_listing_seconds` gauges report each start. Tested
  against a paged bucket of 1,000,000 objects with a slow page: a resume makes
  0 LIST requests at the bucket root and 1 for `s3://bucket/{chain}`. See
  [the README](../../README.md#startup-cost) and
  [the implementation record](../audit/655-resume-cost.md).

Measured results are summarized under [Highlights](#performance).

- **Structure (#525–#530).** Ingestion setup, runtime state and flush windows
  live in `blocks/src/bin/ingestion/` (#525, PR #611); chain-family decisions come

  construction (#530, PR #603).

  mainnet blocks covers both mapping paths and EIP-7702 (#499, PRs #588, #616);
  real-binary ingestion regressions run against a mock Firehose (PR #619); a
  weekly `Network endpoints` workflow checks every built-in endpoint (#535); a
  flaky partition-boundary test gets its own directory (#551, PR #552).
- **Test-only fault hooks (#639).** `FIREPARQ_DEBUG_FAULT`, which fails the
  binary at a named step for recovery tests, is read only by debug builds
  (`cfg!(debug_assertions)`, as built by `cargo test`); the merge hook
  `FIREPARQ_TEST_MERGE_CRASH_AT` went with `merge` (#643). Harnesses that need
  it in an optimized binary can build with
  `CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=true`.
- **Advisory workflow (#639).** The cargo-deny job moved to
  `.github/workflows/advisories.yml`, which `ci.yml` calls and which also runs
  weekly and on manual dispatch. Two deny-level clippy lints in test code were

- **Schema reference.** `docs/schemas/<chain>.md` is generated from the code
  (`cargo run -p blocks --example dump_schemas`) and drift-tested.
- **Dependencies and CI.** See Security under Highlights. The release and Docker
  workflows gained dry-run modes (PRs #627, #628).
- **Delta Lake design and spike (#643).** `docs/design/delta-lake.md` is the plan for
  Delta Lake as the only output format of this release, split into implementation
  lanes. A standalone spike (`spikes/delta-lake/`, outside the workspace and the
  `fireparq` build) commits pre-written parts through `deltalake-core` 1.0.0, runs
  `deltalake` OPTIMIZE and VACUUM beside the writer, and reads the result with
  DuckDB and Polars. The `delta-spike` CI job ran it until L8/L9 removed both,
  once the workspace's tests covered each of its checks (design §1.11).
- **Writer benchmark on fast chains (#658).** `blocks/examples/bench_live_flush`
  measures catch-up throughput, the steady-state margin and per-phase commit
  latency of the real binary on Robinhood and Arbitrum One blocks, against
  local disk and a loopback HTTPS S3 with injected per-request latency. The
  v1.0.0 baseline, measured before the Delta commits, is in
  [658-live-flush-benchmark.md](../audit/658-live-flush-benchmark.md) and sets
  the recommended deployment settings. No writer behavior changed.

  and shares the engine helpers (`blocks/tests/common/mod.rs`); the
  plain-Parquet `polars_check.py` is gone. CI's DuckDB moves from 1.1.1 to

  anonymously with both engines (`FIREPARQ_RGW_ENDPOINT`,
  `FIREPARQ_RGW_BUCKET`; off in CI). The loopback S3 endpoint of the tests
  gained DeleteObjects and real `Last-Modified` times. Record:
  [643-l8-l9-engines-maintenance.md](../audit/643-l8-l9-engines-maintenance.md).
- **Delta Lake dependency and toolchain (#643, L1).** `firehose-parquet` depends
  on `deltalake-core` 1.0.0, with no default features and `rustls`, and without

  delta-rs brings its own Arrow/Parquet 59 and object_store 0.13 beside the

  and properties, creates empty tables and opens them; `build` has written
  through it since L3. The toolchain moves from Rust 1.93 to 1.98 (`rust-toolchain.toml`, the
  `Dockerfile` builder, CI and the release workflow, which now install it with
  `rustup toolchain install`). The `deny.toml` reasons for the quick-xml
  advisories also name object_store 0.13 inside delta-rs.

## Known limitations and follow-ups

- **NEAR `state_changes` is empty (#625).** Every known StreamingFast NEAR
  producer leaves the block's state changes empty, so the rebuilt table (#507)
  has no rows on their output. The mapper is ready for a producer that emits
  them.
- **NEAR, Tron and Cosmos are qualified against RPC and public sources only.**
  Their mapper output was compared value by value with archival RPC, public
  datasets or retained raw blocks, not with a Firehose stream of those chains
  (no usable Firehose quota was available during the audit). EVM, Solana,
  Beacon, Antelope and Bitcoin were compared with Firehose data. Qualification
  against real Firehose data is tracked in #631.
- **#516 stage B (#630).** Stage A overlaps the table work inside one flush,
  but the gRPC stream is still not read while a flush commits. Decoupling
  receive and mapping from the writer needs a reviewed session/frontier
  extension; the requirements are in the
  [design record](../audit/516-concurrency-design.md#stage-b-follow-up).
- **object_store 0.14.** Clearing RUSTSEC-2026-0194 and RUSTSEC-2026-0195
  (quick-xml 0.38, reachable only through S3 XML responses from the configured
  endpoint) needs the breaking object_store 0.14 upgrade (#632). Both
  advisories are ignored in `deny.toml` with that reason.
- **Unmaintained dependencies.** `backoff` (gRPC reconnect back-off,
  RUSTSEC-2025-0012) and `bincode` 1.3 (RUSTSEC-2025-0141) are unmaintained and
  ignored in `deny.toml` until they are replaced (#633).
- **No real-data `gas_changes` fixture.** The offline EVM golden regression
  covers two retained mainnet blocks, but neither records a gas change, so
  `gas_changes` is only covered by synthetic tests (#634).
- **S3 ownership is bucket-wide.** Only one mutating fireparq command
  (`build` or `recovery recover`) can run per bucket; the `deltalake`
  maintenance job needs no ownership and runs beside it (#636). An owner kept after an
  ambiguous `build` request, or after any error of `recovery`, needs
  `recovery release`, which requires the operator's
  confirmation that the provider finished every request of the previous writer;
  providers that cannot give that assurance cannot safely release a stuck owner
  through this command.
- **Protected datasets are bound to their location (#635).** Output authority
  binds the exact output location. A protected dataset copied or moved to
  another path or bucket (for example with `cp -R` or `aws s3 sync`) can still
  be read, but `recovery recover` refuses it (`authoritative output binding
  differs from the selected storage destination`) and it cannot be resumed
  there. There is no relocation procedure yet; build in the final location.
- **No `verify` (#666).** v1.0.0 ships without verifiability. #666 brings
  `verify` back as `merkle_v3` over pinned Delta snapshots, with roots that
  OPTIMIZE and VACUUM do not change.
- **A malformed `./.env` breaks `--help` and `--version` (#637).** The env file
  is loaded before argument parsing, so fix or move a malformed file first.
- **Compacted files lose fireparq's file-level extras.** OPTIMIZE writes new
  files without fireparq's `firehose-parquet.*` footer metadata, Bloom filters
  or sort metadata unless the job's `WriterProperties` enable Bloom filters.
  A table's identity stays in its `fireparq.*` table properties.
- **Non-final history only grows.** Non-final output is an append-only event
  history in Delta tables with `delta.appendOnly`: there is no supported way to
  expire old events. Deleting data files outside the log breaks readers.
- **No atomic multi-table snapshots.** Transactions make each flush
  all-or-nothing for `fireparq`, and each table's Delta log shows a prefix of
  them, but the tables commit one after another (`blocks` last), so a reader
  can see a flush in some tables before others. Take `max(block_num)` of
  `blocks` first and read the other tables up to it for a consistent cut
  (README "Consistent reads across tables"). A glob of table
  directories, which also reads uncommitted and replaced files, is not a
  supported reader.
