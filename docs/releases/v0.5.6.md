# firehose-parquet v0.5.6

`v0.5.6` is a focused operator release that makes three workflows notably better:

1. scanning Parquet rows interactively with pagination,
2. building canonical partition indexes for chains where timestamps are unreliable, and
3. keeping long-running partition builds alive, restartable, and strict about their requested block ranges.

If you mostly use `fireparq` in automation, this release is about making the tool more predictable under real operational pressure.

## Why this release matters

`v0.5.5` tightened schema inspection. `v0.5.6` goes back to the data pipeline itself.

This release helps most when you are:

- exploring large Parquet outputs without dumping the first rows over and over,
- maintaining `partitions.parquet` for Solana or other chains with missing or unreliable timestamps,
- resuming interrupted partition-index builds,
- running long-lived partition maintenance jobs that need to survive quiet network periods,
- enforcing exact block envelopes for deterministic block-range partitioning.

The short version: `v0.5.6` gives operators better pagination, better partition index semantics, and safer long-running behavior.

## Highlights for new users

### 1. `fireparq scan` now supports row pagination with `--offset`

The most visible CLI addition in `v0.5.6` is `--offset` for the `scan` subcommand.

That matters when you want to inspect rows 21-40, 201-220, or any later slice of a file without exporting data elsewhere first.

Examples:

```bash
# Show the first 20 sample rows
fireparq scan ./output/eth-mainnet/blocks/part-000001.parquet

# Show rows 21-40
fireparq scan ./output/eth-mainnet/blocks/part-000001.parquet \
  --offset 20 \
  --limit 20

# Paginate through a directory of Parquet files
fireparq scan ./output/eth-mainnet/blocks/ \
  --offset 100 \
  --limit 25
```

This is especially useful when:

- debugging one problematic row range,
- stepping through large files in order,
- pairing `scan` output with downstream row numbers from validation or review notes.

### 2. `partitions build` can now produce deterministic `block_range` indexes

The headline workflow change in `v0.5.6` is block-number-based partition indexing through `--partition block_range`.

This is particularly valuable for chains like Solana, where timestamps may be missing or unreliable in some ranges.

Examples:

```bash
# Build a canonical block-range partition index for Solana
fireparq partitions build \
  --network solana-mainnet-beta \
  --start-block 0 \
  --stop-block 300000000 \
  --partition block_range \
  --block-range-size 1000000 \
  --output ./output

# Keep extending the same block-range index in live mode
fireparq partitions build \
  --network solana-mainnet-beta \
  --partition block_range \
  --block-range-size 1000000 \
  --output ./output \
  --live
```

What this changes in practice:

- partitions can be defined as exact block envelopes such as `[0, 1000000)`,
- `start_time` and `end_time` can now remain null when the chain cannot provide reliable timestamps,
- the partition index schema is leaner because file-level metadata now carries partition context such as chain, type, interval, and block-range size,
- readers still understand older partition index layouts.

### 3. Resume behavior is better for interrupted block-range builds

Earlier block-range builds could restart too aggressively after interruption. `v0.5.6` fixes that by preserving existing rows and checkpointing bounded block-range progress.

Example:

```bash
# Initial bounded build
fireparq partitions build \
  --network solana-mainnet-beta \
  --start-block 0 \
  --stop-block 100000000 \
  --partition block_range \
  --block-range-size 1000000 \
  --output ./output

# Resume later from the existing canonical index
fireparq partitions build \
  --network solana-mainnet-beta \
  --start-block 0 \
  --stop-block 300000000 \
  --partition block_range \
  --block-range-size 1000000 \
  --output ./output \
  --resume
```

For operators, the important behavior is simple: already completed block-range partitions are preserved, and resumed builds continue from the stored frontier instead of rebuilding from zero.

### 4. Explicit block-range bounds are now strict instead of silently widened

`v0.5.6` also makes block-range input validation stricter. If you provide explicit `--start-block` or `--stop-block`, they must already align to `--block-range-size`.

Example of a rejected command:

```bash
fireparq partitions build \
  --network solana-mainnet-beta \
  --start-block 1 \
  --stop-block 300000000 \
  --partition block_range \
  --block-range-size 10000000 \
  --output ./output
```

Corrected form:

```bash
fireparq partitions build \
  --network solana-mainnet-beta \
  --start-block 0 \
  --stop-block 300000000 \
  --partition block_range \
  --block-range-size 10000000 \
  --output ./output
```

This makes the CLI contract safer for automation because the requested block envelope is no longer silently expanded behind the scenes.

### 5. Idle Firehose connections are more resilient for long-running jobs

Long-running sparse probes and stream sessions now use keepalive settings so stale idle connections recover more cleanly.

There is no new flag to learn here. Existing commands benefit automatically, especially long-lived workflows such as:

```bash
fireparq partitions build \
  --network solana-mainnet-beta \
  --partition block_range \
  --block-range-size 1000000 \
  --output ./output \
  --live
```

This release is meant to reduce the chance that quiet network periods leave a long-lived maintenance process polling on an unhealthy transport.

## Recommended usage patterns

### Paginate through samples while debugging

```bash
fireparq scan ./output/eth-mainnet/blocks/part-000001.parquet \
  --offset 40 \
  --limit 20
```

Use this when you want a later window of rows without changing files or exporting data elsewhere.

### Build a canonical Solana partition index with exact block envelopes

```bash
fireparq partitions build \
  --network solana-mainnet-beta \
  --start-block 0 \
  --stop-block 300000000 \
  --partition block_range \
  --block-range-size 1000000 \
  --output ./output
```

Use this when time-based partitioning is too fragile or too expensive for the chain history you are indexing.

### Resume a previously interrupted bounded build

```bash
fireparq partitions build \
  --network solana-mainnet-beta \
  --start-block 0 \
  --stop-block 300000000 \
  --partition block_range \
  --block-range-size 1000000 \
  --output ./output \
  --resume
```

Use this when you want checkpoint-driven continuation instead of starting over.

## Upgrade guidance

If you are upgrading from `v0.5.5`:

- use `fireparq scan --offset ... --limit ...` when you need paginated row inspection,
- use `--partition block_range` plus `--block-range-size` for deterministic block-based partition indexes,
- expect nullable canonical timestamps to be derived from the block type for chains like Solana,
- expect `--resume` to preserve bounded block-range progress more reliably,
- expect misaligned explicit block-range bounds to fail fast instead of being widened.
