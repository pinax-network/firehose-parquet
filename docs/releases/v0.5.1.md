# firehose-parquet v0.5.1

`v0.5.1` is a focused patch release for teams using `fireparq partitions build` in automation.

This release improves two things:

1. better default and inference behavior for bounded partition-index builds, and
2. a new live mode for continuously extending a canonical `partitions.parquet` index.

If `v0.5.0` made the CLI easier to use, `v0.5.1` makes one of its most important operational workflows easier to automate safely.

## Why this release matters

`partitions build` has become a key step for teams that:

- backfill data in partition-aware windows,
- drive scheduled ingestion from canonical partition indexes,
- maintain a long-lived `partitions.parquet` artifact over time.

`v0.5.1` smooths the defaults for those workflows and adds a dedicated live mode so the same canonical index can keep growing from its stored frontier.

## Highlights for new users

### 1. Better defaults for `partitions build`

This release polishes how `fireparq partitions build` behaves when values can be safely inferred.

The goal is simple: make the command easier to run repeatedly without forcing you to restate every parameter every time.

This work includes improvements around:

- preserving day-based partition compatibility in lookups,
- cleaner partition naming expectations,
- more practical defaults and naming for repeated builds,
- better fit for automation and scheduled jobs.

Examples:

```bash
# Build a bounded canonical partition index
fireparq partitions build \
  --network mainnet \
  --start-block 10000000 \
  --stop-block 10020000 \
  --partition date \
  --output ./output

# Build multiple granularities into the same canonical index
fireparq partitions build \
  --network mainnet \
  --start-block 10000000 \
  --stop-block 10020000 \
  --partition date,hour \
  --output ./output

# Continue a bounded build with fewer repeated inputs
fireparq partitions build \
  --network mainnet \
  --start-block 10020000 \
  --stop-block 10040000 \
  --partition date,hour \
  --output ./output
```

For new users, the practical takeaway is that `partitions build` is now easier to treat as a repeatable maintenance command instead of a one-off indexing tool.

### 2. New `--live` mode for `partitions build`

The biggest new user-facing feature in `v0.5.1` is live mode.

`--live` lets `fireparq partitions build` keep extending an existing canonical `partitions.parquet` artifact from its latest covered frontier.

That makes it a strong fit for:

- recurring scheduled jobs,
- continuously maintained partition indexes,
- backfill-to-live handoffs.

Example:

```bash
# Continue extending the canonical index in live mode
fireparq partitions build \
  --network mainnet \
  --partition date,hour \
  --output ./output \
  --live
```

Important semantics:

- `--live` uses existing `partitions.parquet` rows as the restart anchor,
- `--stop-block` is not required in live mode,
- `--stop-block` is incompatible with `--live`,
- if there is no existing frontier, `--start-block` may still be needed.

That gives operators a clean model:

- use bounded builds for deterministic backfills,
- use `--live` once you want the index to keep moving forward.

### 3. Cleaner automation path for partition-driven ingestion

Combined with the partition tooling added in previous releases, `v0.5.1` makes a nice operational pattern possible:

1. create a canonical partition index with `partitions build`,
2. keep it current with `partitions build --live`,
3. resolve or shard from that index for ingestion workers.

Examples:

```bash
# Keep the canonical index current
fireparq partitions build \
  --network mainnet \
  --partition date,hour \
  --output ./output \
  --live

# Resolve one partition from that index
fireparq partitions resolve \
  --partitions-index ./output/mainnet/partitions.parquet \
  --partition-type hour \
  --partition-value '2015-07-30 15:00:00' \
  --partition-chain mainnet

# Shard work across workers
fireparq partitions shard \
  --partitions-index ./output/mainnet/partitions.parquet \
  --partition-type hour \
  --shard-count 4 \
  --shard-index 1
```

This release does not introduce a brand-new subsystem, but it does make the partition-index lifecycle feel more complete.

## Suggested upgrade path

If you already use `partitions build`:

- keep bounded builds for explicit backfill ranges,
- move recurring maintenance jobs to `--live`,
- review any automation that assumes `--stop-block` is always required,
- keep using the `fireparq` binary name introduced in `v0.5.0`.
