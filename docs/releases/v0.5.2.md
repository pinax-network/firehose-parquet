# firehose-parquet v0.5.2

`v0.5.2` is a focused operational release that improves how `fireparq partitions build` finds partition boundaries, records probe metadata, and exits cleanly during live operation.

This release also removes the now-unneeded `partitions.lookup.json` sidecar path, keeping `partitions.parquet` as the single canonical source of truth for partition-index workflows.

If `v0.5.1` made `partitions build` easier to automate, `v0.5.2` makes it more efficient, more deterministic, and easier to trust in production.

## Why this release matters

Partition indexes are increasingly being used as operational control planes for ingestion.

That means `partitions build` needs to be:

- fast enough for repeated runs,
- explicit enough to explain what it is doing,
- resilient enough to stop promptly when an operator asks it to stop,
- strict enough to avoid stale or ambiguous metadata.

`v0.5.2` is about those operational guarantees.

## Highlights for new users

### 1. Sparse probes make `partitions build` more efficient

The biggest change in this release is the move toward sparse probing for partition-boundary discovery.

Instead of relying on broader scanning behavior, `partitions build` now uses a much more targeted probing strategy to locate partition boundaries and exact closing ranges.

That makes bounded and live builds more efficient and more predictable.

Examples:

```bash
# Bounded build with the newer sparse-probe behavior
fireparq partitions build \
  --network mainnet \
  --start-block 10000000 \
  --stop-block 10020000 \
  --partition date,hour \
  --output ./output

# Live build continues using sparse probes instead of a normal block stream
fireparq partitions build \
  --network mainnet \
  --partition date,hour \
  --output ./output \
  --live
```

Practical effect:

- bounded builds tighten boundary search,
- live builds poll via sparse probes,
- exact block fetches are used for probe paths,
- progress and boundary behavior are easier to reason about.

### 2. Probe metadata is stricter and clearer

This release hardens how partition probe metadata is recorded and normalized.

That matters because partition indexes are only as trustworthy as the metadata behind the discovered boundaries.

`v0.5.2` improves this by:

- hardening probe metadata expectations,
- making the `chain` column required and non-nullable in `partitions.parquet`,
- normalizing missing probe timestamps using nearby subsequent finalized blocks when possible,
- avoiding ambiguous or weak probe-derived partition records.

For a new user, the short version is: the partition index is now stricter about what it considers valid enough to write.

### 3. Live builds stop more promptly on shutdown

Operators running `partitions build --live` often need the process to stop quickly and cleanly during deploys, maintenance windows, or manual restarts.

This release improves shutdown handling so live partition probes are interrupted promptly on Ctrl-C and SIGTERM.

Example:

```bash
fireparq partitions build \
  --network mainnet \
  --partition date,hour \
  --output ./output \
  --live
```

Then stop it with Ctrl-C when needed.

In `v0.5.2`, the process is better at:

- interrupting live frontier probes,
- interrupting boundary search loops,
- checkpointing and exiting with clearer intent.

### 4. The lookup sidecar is removed

Earlier releases added an optional `partitions.lookup.json` sidecar to accelerate some partition lookups.

`v0.5.2` removes that sidecar support and recenters the workflow around the canonical `partitions.parquet` artifact alone.

That simplifies the mental model for new users:

- there is one canonical partition-index artifact,
- you do not need to manage a second lookup file,
- partition resolution behavior depends on the parquet index itself.

If you were already using the canonical parquet index directly, this makes the workflow simpler rather than more complex.

## Recommended usage patterns

### Bounded partition-index build

```bash
fireparq partitions build \
  --network mainnet \
  --start-block 10000000 \
  --stop-block 10040000 \
  --partition date,hour \
  --output ./output
```

Use this when you want a deterministic backfill range.

### Live partition-index maintenance

```bash
fireparq partitions build \
  --network mainnet \
  --partition date,hour \
  --output ./output \
  --live
```

Use this when you want to keep a canonical `partitions.parquet` index moving forward from its latest frontier.

### Downstream partition-driven workflows

```bash
# Resolve a partition from the canonical index
fireparq partitions resolve \
  --partitions-index ./output/mainnet/partitions.parquet \
  --partition-type hour \
  --partition-value '2015-07-30 15:00:00' \
  --partition-chain mainnet

# Shard partition work across workers
fireparq partitions shard \
  --partitions-index ./output/mainnet/partitions.parquet \
  --partition-type hour \
  --shard-count 4 \
  --shard-index 1
```

## Upgrade guidance

If you are upgrading from `v0.5.1`:

- keep using `partitions.parquet` as the canonical index,
- remove any operational dependency on `partitions.lookup.json`,
- expect `partitions build` to rely more heavily on sparse probe logic,
- use `--live` for long-running index maintenance and rely on the improved shutdown behavior.
