# firehose-parquet v1.4.0

`v1.4.0` is a minor release of [v1.3.1](v1.3.1.md). It adds a parallel
backfill: `fireparq backfill open` plans block ranges (lanes) in a new S3
dataset, one `build` per lane fills them at the same time, and `fireparq
backfill seal` turns the result into an ordinary dataset that `build`
continues live. Existing datasets are unchanged: every block family keeps its
schemas and digests, so a v1.3.x dataset resumes as it is and no rebuild is
needed.

## Upgrade

- **Writers and maintenance jobs:** move to the new image tag
  (`ghcr.io/pinax-network/firehose-parquet:1.4.0`). Nothing else changes for
  any block family. Files written after the upgrade carry
  `firehose-parquet.version` `1.4.0`; maintenance leaves the key out of a
  compacted day that spans the upgrade.
- **S3 writers read one more object at start:**
  `.fireparq-ingest/backfill.json`, absent in every dataset that was not
  opened as a parallel backfill. A read that fails for another reason than
  "not found", or takes longer than 10 seconds, stops the start with
  `backfill control record read failed`. The writer's S3 user already reads
  that prefix.
- **Rollback:** a dataset that was never a parallel backfill goes back to
  v1.3.1 as it is. Run only 1.4.0 or later on a backfill that is not sealed.
- **Parallel backfill** is opt-in; see [Parallel backfill](../parallel-backfill.md)
  before the first one, and the first known issue.

## Known issues

- **Parallel backfill has not run on production storage or a real chain
  yet.** Its tests use a mock Firehose and a loopback S3 server, with ranges
  of a few hundred blocks. Not measured: Ceph RGW, the run time and memory of
  the seal's range check over 100M blocks or more, and many lanes committing
  beside the maintenance job for days. An older release is expected to refuse
  a backfill that is not sealed, and to resume a sealed one; neither was run.
  Seal and validate the first backfill before readers get the bucket.
- **A writer used twice its usual memory after a resume**
  ([#723](https://github.com/pinax-network/firehose-parquet/issues/723)): on
  Ethereum near block 22.8M (`--flush-memory-bytes` 1 GiB), one resumed
  writer grew to 8 GiB in 20 minutes while its predecessor and successor held
  2 to 4 GiB on the same blocks. Its tracked buffer estimates were the same as
  theirs; it ran about 100 threads instead of 11 to 28. The cause is not
  known. Leave a memory limit well above the usual footprint, for each lane
  of a parallel backfill too.
- **Overlapping maintenance runs duplicate rows**
  ([#717](https://github.com/pinax-network/firehose-parquet/issues/717)): two
  `fireparq maintenance` runs that compact the same date at once both commit,
  and the date's rows are duplicated. deltalake-core 1.0.0 does not treat two
  compactions removing the same files as a conflict. `concurrencyPolicy:
  Forbid` covers only one CronJob, so schedule a lake's maintenance CronJobs
  apart, or suspend the frequent job while a VACUUM job runs. Lanes of a
  parallel backfill only append, so they are not affected.
  `fireparq hypercore-reference` is not affected: its commits never retry.
- **Non-final output with a reorg deeper than one block never compacts**
  ([#715](https://github.com/pinax-network/firehose-parquet/issues/715)): only
  `--final-blocks-only=false` lakes are affected; the day keeps its parts and
  every maintenance run reports it.
- **SEC operations** ([#711](https://github.com/pinax-network/firehose-parquet/issues/711)):
  unchanged from v1.2.0. A live SEC writer can exit with `reconnect stalled`
  after two disconnects in one quiet day, and the 512 MiB SEC message default
  admits windows larger than the documented 3 GiB of writer memory can map.
- **HyperCore endpoint:** blocks 846903300–846903312, before the data origin,
  are still missing upstream
  ([firehose-hypercore#31](https://github.com/pinax-network/firehose-hypercore/issues/31)).

## New features

- **Parallel backfill** (#725, #726). A new dataset's history can be written
  by many `build` processes at once instead of one sequential writer.
  - **`fireparq backfill open`** takes the options of `build` plus
    `--stop-block` and `--lane-blocks`, in a new, empty S3 dataset root. It
    writes the plan (`.fireparq-ingest/backfill.json`) and creates the empty
    tables.
  - **Lanes:** one `fireparq build` per planned range, with exactly its
    `--start-block` and `--stop-block`, as many at a time as wanted. Each lane
    has its own owner, checkpoint and journal under
    `.fireparq-ingest/lanes/<start>-<stop>/` and writes its parts straight to
    the tables; nothing is staged or copied. A failed lane is rerun, and
    blocks only itself.
  - **`fireparq backfill status`** counts the complete, running, stopped and
    not started lanes, and lists the first ones that are not complete.
  - **`fireparq backfill seal`** refuses unless every lane is complete and
    `blocks` holds exactly the planned range: no gap, no duplicate, every
    block linked to its parent. It then writes the dataset's authority, and
    `fireparq build` without a range continues live from the stop block.
  - **Until the seal** every other `build` into the root is refused, the
    [frontier rule](../reading-tables.md#consistent-reads-across-tables) does
    not hold, and the maintenance job may run; give it a checkpoint more
    often than hourly.
  - **`recovery status` and `recovery release`** take `--lane <start>-<stop>`
    for a lane's own owner.
  - **Limits:** S3 output, final-only streams, and chains that have every
    block number of the range (not Solana, NEAR or Beacon). `--start-block`
    must not be below the chain's first block, and an existing dataset cannot
    be backfilled below its start.
  - [Parallel backfill](../parallel-backfill.md) has the rules and the
    recovery commands.
