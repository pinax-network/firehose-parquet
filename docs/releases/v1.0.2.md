# firehose-parquet v1.0.2

`v1.0.2` is a patch release of [v1.0.1](v1.0.1.md). A transient error on a
read of a Delta log no longer ends `build`, and a new dataset no longer logs
an ERROR line for every table it creates. The Delta maintenance job is now a
Rust binary, `fireparq-maintenance`, which skips a table the writer has not
created yet, and the repository is Rust-only. It changes no output format,
schema, CLI flag or dataset state. A v1.0.1 dataset resumes as it is, and no
rebuild is needed.

## Upgrade

- **Maintenance image.** `ghcr.io/pinax-network/firehose-parquet-maintenance`
  keeps its name and settings and now runs the `fireparq-maintenance` binary
  as its entrypoint (on `debian:bookworm-slim` with CA certificates, as user
  65534). The CronJobs of `deploy/examples/delta-maintenance-cronjob.yaml`
  need only the new tag. A deployment that overrode the container `command`
  with `python /opt/delta_maintenance.py` must drop the override.
- **Release tarballs** also ship `fireparq-maintenance`.

## New features

### The Delta maintenance job is a Rust binary

`fireparq-maintenance` (the workspace crate `maintenance/`) replaces
`scripts/delta_maintenance.py`. It runs the same off-the-shelf delta-rs
operations (`deltalake-core` 1.0.0: OPTIMIZE with DataFusion 55, VACUUM,
`create_checkpoint`, `cleanup_metadata`) and keeps the script's interface:
the same environment variables, per-table order (OPTIMIZE of closed dates with
more than one file, lite or full VACUUM, a checkpoint only after a successful
VACUUM, log cleanup; OPTIMIZE and VACUUM write no checkpoint of their own),
JSON-line output and exit statuses (0; 1 when a table failed; 2 for a
configuration error). The output adds a `skipped` line per missing table,
`skipped` in `done` and the binary's `version` in `start`. A conflict is now
only a lost commit race; any other commit error fails the table (the Python
bindings reported every transaction error as a conflict). The job sends no
`If-Match` request, so Ceph RGW 19.2's `If-Match` quirk (#678) does not
affect it. See README "Delta maintenance".

## Fixes

### The maintenance job skips a table that does not exist yet (#680)

`scripts/delta_maintenance.py` reported a table the writer had not created
yet as failed (`TableNotFoundError`, exit 1): on riv-dev1 two hourly runs
failed that way while the writer was stopped before creating its tables.
`fireparq-maintenance` reports such a table as `skipped` and exits 0. A table
that exists but cannot be read still fails.


### Delta log reads retry transient errors (#680)

On Ceph RGW 19.2.3, one `build` exited 1 at startup when a single
`GET <table>/_delta_log/_last_checkpoint` failed after 14 ms with
`HTTP error: error sending request`, a connection-level error. The Delta log
client sent every request exactly once. That is required for
commits: object_store would resend a conditional commit on a 5xx or a lost
connection, and a first copy that landed would turn the resend into a 412
and a second commit at the next version. Reads carry no such risk. The run
was safe (the owner was released and the next start resumed), but a
continuous writer paid a restart for it.

The log client now resends an idempotent read, a `GET` or `HEAD` (log
objects, checkpoints, `_last_checkpoint`, listings of `_delta_log/`, and
what delta-rs reads while loading a snapshot), up to 3 attempts in all, when
it gets no response (a connection error, reset or timeout) or a 408, 429 or
5xx. Each retry waits a jittered exponential backoff (100–200 ms before the
second attempt, 200–400 ms before the third) and logs a warning:

```
WARN retrying an idempotent Delta log read after a transient error method=GET
path="/<bucket>/<table>/_delta_log/_last_checkpoint" attempt=1 attempts=3 backoff_ms=178
error=HTTP error: error sending request: …
```

Every other request, including the conditional `PUT` of a log commit, is
still sent once. A commit whose outcome is unknown still fails the run, still
releases the S3 owner, and is still resolved by the next start from the
table's `txn` (design §3.5). fireparq's own control-state and part requests
are unchanged.

### No ERROR lines when a dataset is created (#680)

A new dataset on S3 logged one line per table while its tables were created:

```
ERROR error=Generic delta kernel error: No files in log segment
```

delta-rs's kernel logs this itself when it is asked to open a table that has
no log yet, before fireparq sees the expected "absent" answer and creates
the table. While tables may be created, `build` now lists each table's log
first and creates a table without one directly. A table that fails to open
for any other reason still logs and fails as before.

See the [record](../audit/680-delta-read-retries.md).

## Internal

- **The repository is Rust-only ([record](../audit/rust-only.md)).** No code
  or dependency needs Python, and CI installs none (it checks that no Python
  file is tracked). The Delta tests read through delta-rs (`deltalake-core`
  snapshots and the active files' rows) and the checksum-verified DuckDB CLI,
  and run the maintenance binary (`FIREPARQ_MAINTENANCE`, required in CI by
  `FIREPARQ_REQUIRE_MAINTENANCE`); the Polars assertions are dropped, since
  Polars' `scan_delta` reads through delta-rs. The README's Polars examples
  stay, for users.
- **The writer links no DataFusion, not even in tests.** Only `maintenance/`
  enables `deltalake-core`'s `datafusion` feature, and nothing depends on it.
  CI checks that `cargo tree -p blocks` lists no DataFusion crate, runs
  `cargo test -p fireparq-maintenance` and
  `cargo test --workspace --exclude fireparq-maintenance` separately (one run
  would unify DataFusion's features, such as serde_json's `preserve_order`,
  into the writer under test), and the release workflow builds `fireparq` and
  `fireparq-maintenance` in separate cargo invocations.
- **`docs/audit/*.py` removed.** The historical Python validation tooling of
  the audit records is in git history at
  [v1.0.1](https://github.com/pinax-network/firehose-parquet/tree/v1.0.1/docs/audit);
  the records link it there.
