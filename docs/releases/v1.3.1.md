# firehose-parquet v1.3.1

`v1.3.1` is a patch release of [v1.3.0](v1.3.0.md). A writer that resumes deep
in a backfill now reports its catch-up when its commits take longer than one
5-second pace sample (#721), and dependency updates clear nine security
advisories. Output, schemas and dataset state are unchanged: a v1.3.0 dataset
resumes as it is, and no rebuild is needed.

## Upgrade

- **Writers and maintenance jobs:** move to the new image tag
  (`ghcr.io/pinax-network/firehose-parquet:1.3.1`). Nothing else changes for
  any block family. Files written after the upgrade carry
  `firehose-parquet.version` `1.3.1`; maintenance leaves the key out of a
  compacted day that spans the upgrade.
- **Alerts on `firehose_parquet_catching_up == 0`** with a large
  `firehose_parquet_block_time_lag_seconds` no longer fire for such a
  backfill once its writer runs 1.3.1.

## Known issues

- **A writer used twice its usual memory after a resume**
  ([#723](https://github.com/pinax-network/firehose-parquet/issues/723)): on
  Ethereum near block 22.8M (`--flush-memory-bytes` 1 GiB), one resumed
  writer grew to 8 GiB in 20 minutes while its predecessor and successor held
  2 to 4 GiB on the same blocks. Its tracked buffer estimates were the same as
  theirs; it ran about 100 threads instead of 11 to 28. The cause is not
  known. Leave a memory limit well above the usual footprint.
- **Overlapping maintenance runs duplicate rows**
  ([#717](https://github.com/pinax-network/firehose-parquet/issues/717)): two
  `fireparq maintenance` runs that compact the same date at once both commit,
  and the date's rows are duplicated. deltalake-core 1.0.0 does not treat two
  compactions removing the same files as a conflict. `concurrencyPolicy:
  Forbid` covers only one CronJob, so schedule a lake's maintenance CronJobs
  apart, or suspend the frequent job while a VACUUM job runs.
  `fireparq hypercore-reference` is not affected: its commits never retry.
- **Non-final output with a reorg deeper than one block never compacts**
  ([#715](https://github.com/pinax-network/firehose-parquet/issues/715)): only
  `--final-blocks-only=false` lakes are affected; the day keeps its parts and
  every maintenance run reports it.
- **SEC operations** ([#711](https://github.com/pinax-network/firehose-parquet/issues/711)):
  unchanged from v1.2.0. A live SEC writer can exit with `reconnect stalled`
  after two disconnects in one quiet day, and the 512 MiB SEC message default
  admits windows larger than the documented 3 GiB of writer memory can map.
- **HyperCore endpoint:** blocks 846903300–846903312, before the data origin,
  are still missing upstream
  ([firehose-hypercore#31](https://github.com/pinax-network/firehose-hypercore/issues/31)).

## Fixes

- **A replay with commits of 5 seconds or more is detected as a catch-up**
  (#721, #722).
  - **What was wrong:** a writer that started deep in a backfill could stay
    `caught_up` for the whole replay: `firehose_parquet_catching_up` stayed 0,
    flushes carried `pace="caught_up"`, and `--flush-interval-secs` stayed
    armed. It happened when each flush's commit blocked the stream for longer
    than one 5-second pace sample and the blocks between two commits arrived
    in less than that. Seen on Ethereum near block 22.8M with
    `--flush-memory-bytes` 1 GiB (240 blocks over 4 s, then a 5.4 to 6.5 s
    commit). A writer that entered the catch-up earlier, such as one started
    at genesis, kept it.
  - **Now:** the writer's own commit is no longer measured as a wait of the
    stream, and it does not count toward the 30 seconds of evidence that
    start a catch-up. The writer above switches after about 80 seconds.
  - **Operators:** nothing to do. An alert on `firehose_parquet_catching_up
    == 0` and a large `firehose_parquet_block_time_lag_seconds` no longer
    fires for such a backfill. No output, schema or dataset state changes.
  - [Record](../audit/659-adaptive-flush.md#the-writers-own-commits).
- **Dependency updates for nine security advisories** (#722). Only
  `Cargo.lock` changed:
  - rustls-webpki 0.103.16 (RUSTSEC-2026-0382) and webpki-root-certs 1.0.11
    (RUSTSEC-2026-0383): certificate paths through distrusted emSign
    intermediates could be accepted.
  - zstd 0.13.4 and 0.14.3 (RUSTSEC-2026-0391: data from an abandoned stream
    leaks into the next stream on a reused context), zstd-safe 7.4.0 and
    8.2.0 (RUSTSEC-2026-0398, RUSTSEC-2026-0403) and zstd-sys 2.1.2
    (RUSTSEC-2026-0410). The bundled zstd library stays 1.5.7, so compressed
    output is unchanged.
  - tokio 1.53.3 (RUSTSEC-2026-0386: `AsyncFd::new` violates I/O safety).
  - pulldown-cmark 0.13.6 (RUSTSEC-2026-0414, RUSTSEC-2026-0433), used only
    at build time by prost-build.

## Internal

- **`local_resume_walks_no_data_directory` no longer depends on directory
  order** (#722): the recovery tree walk it compares against may stop at the
  unreadable directory before the nested symlink, as it does on the current
  CI runners.
