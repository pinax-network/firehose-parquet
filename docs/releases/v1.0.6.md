# firehose-parquet v1.0.6

`v1.0.6` is a patch release of [v1.0.5](v1.0.5.md). `fireparq-maintenance`
now compacts with its own planner, which keeps the rows in the order
`fireparq build` wrote them, and repairs the days that earlier versions
compacted out of that order. It changes no output format, schema, CLI flag or
dataset state: a v1.0.5 dataset resumes as it is, and no rebuild is needed.

## Upgrade

- **Maintenance image.** `ghcr.io/pinax-network/firehose-parquet-maintenance`
  needs the new tag.
  - Drop `OPTIMIZE_MAX_CONCURRENT_TASKS`; it is ignored if set.
  - From the first run, new days are concatenated in the writer's order.
  - Days an earlier version compacted are sorted back into it,
    `OPTIMIZE_REPAIR_DATES` (default 1) per table per run, newest first.
  - Until a lite VACUUM deletes them (`VACUUM_RETENTION_HOURS` after the
    repair), a repaired day's old files stay in storage beside the new ones:
    allow up to one more copy of the repaired days in the bucket's quota.
- **Writer image.** `ghcr.io/pinax-network/firehose-parquet` changes only its
  version.

## Fixes

- **Compaction keeps the writer's row order**
  ([#690](https://github.com/pinax-network/firehose-parquet/issues/690),
  [#691](https://github.com/pinax-network/firehose-parquet/pull/691)).
  - **What was wrong:** up to v1.0.5, `fireparq-maintenance` ran delta-rs's
    OPTIMIZE. It bins a day's files newest first and writes a parallel
    DataFusion scan's batches as they arrive. Its compacted files held a day's
    blocks out of order and some blocks in pieces, and now and then a block's
    own rows were out of their Firehose order: on riv-dev1, one block a day in
    eth `logs` and in `calls`. No row was lost or changed.
  - **New days:** the job plans a day by its files' `block_num` ranges and
    concatenates writer parts in block order, each file read start to finish.
  - **Old days:** files out of order are sorted back by `block_num` and the
    table's in-block key, a window of decoded blocks at a time
    (`OPTIMIZE_REPAIR_WINDOW_BYTES`, default 256 MiB; about 1.3 GiB peak on
    eth `calls`). Each key was verified strictly increasing on every writer
    part of eth, Base and BSC, and `evm_golden` checks it on the reviewed
    mainnet blocks.
  - **Safety:** a tie on the key, a block out of order or a row count that
    differs from `numRecords` fails the day, which then commits nothing. A
    table with no known key is never repaired.
  - **Marking:** written files carry the log tag `fireparq.rowOrder = writer`
    and the footer key `fireparq-maintenance.row_order = writer`.
  - **More output:** the `table` line's `compacted` entries add `rows` and
    `repaired_bins`, and the line adds `repairs_deferred` and
    `repairs_unsupported`.
  - See [Row order](../delta-maintenance.md#row-order) and the
    [record](../audit/690-compaction-row-order.md).
