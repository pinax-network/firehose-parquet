# firehose-parquet v1.5.0

`v1.5.0` is a minor release of [v1.4.0](v1.4.0.md). Lanes of a parallel
backfill now commit to the Delta logs in batches instead of on every flush
(#728), and `fireparq recovery rebind` lets a dataset copied to a new root
resume there (#635). Existing datasets are unchanged: every block family keeps
its schemas and digests, so a v1.4.0 dataset resumes as it is and no rebuild
is needed.

## Upgrade

- **Writers and maintenance jobs:** move to the new image tag
  (`ghcr.io/pinax-network/firehose-parquet:1.5.0`). Nothing else changes for
  an ordinary dataset: its writer still commits every flush before it accepts
  it. Files written after the upgrade carry `firehose-parquet.version`
  `1.5.0`; maintenance leaves the key out of a compacted day that spans the
  upgrade.
- **A parallel backfill begun with v1.4.0:** rerun its lanes with the new
  image. Complete lanes stay complete, and a stopped or failed lane resumes
  from its own checkpoint and commits in batches from then on. Nothing is
  migrated.
- **Rollback:** an ordinary dataset that was not rebound goes back to v1.4.0
  as it is. Run only 1.5.0 or later on a backfill that is not sealed once a
  1.5.0 lane has written to it: v1.4.0 refuses a lane that owes files. A
  rebound dataset under v1.4.0 was not tried.
- **Full VACUUM beside a backfill:** a lane's accepted files are in no Delta
  log until its next batch. Keep the weekly full VACUUM away from a lane that
  has been stopped for its retention (7 days)
  ([details](../parallel-backfill.md#until-the-seal)). The frequent job's
  VACUUM is not affected.

## Known issues

- **The batched lane commits and `recovery rebind` have not run on production
  storage yet.** Their tests use a mock Firehose, InMemory stores and a
  loopback S3 server. v1.4.0 lanes did run on Ceph RGW with real chain data,
  which is where #728 was measured. Still not measured: a lane's batch on
  Ceph RGW, a rebind there, and the run time and memory of the seal's range
  check over tens of millions of blocks. Rehearse a rebind on a throwaway
  copy first, and seal and validate a backfill before readers get the bucket.
- **Many lanes still share the Delta logs** (#728): a batch is one commit per
  table, so lanes lose far fewer attempts, but the 25-attempt limit is
  unchanged. Beside lanes, the maintenance job still compacts a table before
  it checkpoints it, so its first run over a long log takes hours.
- **A writer used twice its usual memory after a resume**
  ([#723](https://github.com/pinax-network/firehose-parquet/issues/723)): on
  Ethereum near block 22.8M (`--flush-memory-bytes` 1 GiB), one resumed
  writer grew to 8 GiB in 20 minutes while its predecessor and successor held
  2 to 4 GiB on the same blocks. Its tracked buffer estimates were the same as
  theirs; it ran about 100 threads instead of 11 to 28. The cause is not
  known. Leave a memory limit well above the usual footprint, for each lane
  of a parallel backfill too.
- **Overlapping maintenance runs duplicate rows**
  ([#717](https://github.com/pinax-network/firehose-parquet/issues/717)): two
  `fireparq maintenance` runs that compact the same date at once both commit,
  and the date's rows are duplicated. deltalake-core 1.0.0 does not treat two
  compactions removing the same files as a conflict. `concurrencyPolicy:
  Forbid` covers only one CronJob, so schedule a lake's maintenance CronJobs
  apart, or suspend the frequent job while a VACUUM job runs. Lanes of a
  parallel backfill only append, so they are not affected.
  `fireparq hypercore-reference` is not affected: its commits never retry.
- **Non-final output with a reorg deeper than one block never compacts**
  ([#715](https://github.com/pinax-network/firehose-parquet/issues/715)): only
  `--final-blocks-only=false` lakes are affected; the day keeps its parts and
  every maintenance run reports it.
- **SEC operations** ([#711](https://github.com/pinax-network/firehose-parquet/issues/711)):
  unchanged from v1.2.0. A live SEC writer can exit with `reconnect stalled`
  after two disconnects in one quiet day, and the 512 MiB SEC message default
  admits windows larger than the documented 3 GiB of writer memory can map.
- **HyperCore endpoint:** blocks 846903300–846903312, before the data origin,
  are still missing upstream
  ([firehose-hypercore#31](https://github.com/pinax-network/firehose-hypercore/issues/31)).

## New features

- **Relocate a dataset: `fireparq recovery rebind` (#635).** A stopped dataset
  copied to a new root (`cp -R`, `aws s3 sync`) on the same storage service
  resumes there after `fireparq recovery rebind <new root> --from <old root>`.
  It checks that the copy is complete and that the old root is quiet, then
  changes only the copy's binding: `state.json`, each Delta table's
  `fireparq.descriptor` (one `SET TBLPROPERTIES` commit per table, `blocks`
  last) and the cursor mirror. The old root is only read, and a rerun completes
  an interrupted rebind. `build` and `recovery recover` now name the command when
  they find a dataset bound to another root. See [Relocating a
  dataset](../cursor-and-resume.md#relocating-a-dataset).

## Performance

- **Backfill lanes commit to the Delta logs in batches (#728).** A lane
  committed every flush to logs that all lanes share: ten lanes of the `base`
  backfill lost 1.3 attempts per commit, spent most of their time committing
  and failed at the 25-attempt limit. A lane now accepts each flush in its own
  state and commits its files together, one commit per table: every
  `--lane-commit-flushes` flushes (`LANE_COMMIT_FLUSHES`, default 64), when it
  finishes, on SIGTERM and at every start. `backfill status` reports
  `uncommitted_flushes`. Lanes of a backfill begun with v1.4.0 resume under
  v1.5.0; do not go back, since v1.4.0 refuses the state of a lane that
  owes files. Keep the weekly full VACUUM away from a lane stopped for 7 days
  ([details](../parallel-backfill.md#until-the-seal)).
