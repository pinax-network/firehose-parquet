# firehose-parquet v0.5.3

`v0.5.3` is a focused reliability release for long-running `fireparq partitions build` jobs.

The headline improvement is continuous checkpointing: bounded and live partition-index builds now save progress earlier and more often, so long runs are easier to resume and less fragile during interruptions.

This release also tightens the operator experience by making partitions rollover logging more compact and easier to scan.

## Why this release matters

By `v0.5.2`, `partitions build` had become faster and more deterministic. `v0.5.3` takes the next operational step: making those long-running builds safer to interrupt and easier to recover.

That matters most when you are:

- maintaining a canonical `partitions.parquet` index over long periods,
- running large bounded backfills that may take a while,
- operating live partition-index maintenance jobs,
- restarting jobs during deploys or infrastructure interruptions.

The short version: `v0.5.3` reduces how much progress you risk losing between checkpoints.

## Highlights for new users

### 1. Long-running `partitions build` jobs checkpoint continuously

The biggest improvement in `v0.5.3` is that `partitions build` now checkpoints during long runs instead of waiting too long between writes.

This applies to:

- bounded builds,
- live builds,
- runs with many partition rollovers,
- runs where progress should be preserved as soon as useful rows exist.

Examples:

```bash
# Bounded build with continuous checkpointing
fireparq partitions build \
  --network mainnet \
  --start-block 10000000 \
  --stop-block 10080000 \
  --partition date,hour \
  --output ./output

# Live build with repeated checkpointing over time
fireparq partitions build \
  --network mainnet \
  --partition date,hour \
  --output ./output \
  --live
```

What this improves in practice:

- the first checkpoint is written as soon as the first row exists,
- long runs checkpoint by elapsed time instead of only at the end,
- partition rollovers can trigger checkpoint opportunities,
- interrupted runs resume from fresher progress.

For a new user, this means `partitions build` is now better suited to “set it, monitor it, and safely restart it later” workflows.

### 2. Recovery is better for both bounded and live modes

`v0.5.3` is not just about live mode — bounded builds benefit too.

That is important because bounded builds are often used for large historical coverage, where a failed run can otherwise waste a lot of time.

Example:

```bash
# Large bounded historical build
fireparq partitions build \
  --network mainnet \
  --start-block 5000000 \
  --stop-block 15000000 \
  --partition date,hour \
  --output ./output
```

With the checkpointing changes in this release, that kind of run is more resilient if it gets interrupted partway through.

### 3. Rollover logs are more compact and easier to read

This release also trims partitions rollover logging so operators can follow progress without being overwhelmed by noisy output.

That helps when:

- watching long jobs in CI or terminals,
- diagnosing slow progress,
- scanning logs after the fact.

This is a smaller feature than checkpointing, but it improves the real operator experience for anyone who watches partition jobs regularly.

## Recommended usage patterns

### Large bounded build

```bash
fireparq partitions build \
  --network mainnet \
  --start-block 10000000 \
  --stop-block 20000000 \
  --partition date,hour \
  --output ./output
```

Use this for deterministic backfills while benefiting from mid-run checkpoint persistence.

### Long-running live maintenance job

```bash
fireparq partitions build \
  --network mainnet \
  --partition date,hour \
  --output ./output \
  --live
```

Use this when you want the canonical partition index to keep moving forward while preserving recoverable progress throughout the run.

### Downstream partition-driven workflows still stay the same

```bash
# Resolve one partition from the canonical index
fireparq partitions resolve \
  --partitions-index ./output/mainnet/partitions.parquet \
  --partition-type hour \
  --partition-value '2015-07-30 15:00:00' \
  --partition-chain mainnet

# Shard partition work across workers
fireparq partitions shard \
  --partitions-index ./output/mainnet/partitions.parquet \
  --partition-type hour \
  --shard-count 4 \
  --shard-index 1
```

The value of `v0.5.3` is that the upstream partition index feeding these workflows is now persisted more safely during long builds.

## Upgrade guidance

If you are upgrading from `v0.5.2`:

- keep using the same `partitions build` commands,
- expect checkpoints to be written earlier and more often,
- expect cleaner rollover logs during long runs,
- treat this release as an operational reliability upgrade rather than a CLI-surface change.
