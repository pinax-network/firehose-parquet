# firehose-parquet v0.4.0

`v0.4.0` is a minor release focused on three things:

1. making long-running backfills more resilient,
2. turning partition indexes into a first-class workflow, and
3. introducing a much more practical verification surface.

If you are new to `firehose-parquet`, the big takeaway is simple: you can now build and query canonical partition indexes, run partition-aware ingestion without doing block math by hand, verify datasets with clearer profiles and reports, and rely on better defaults for reconnect/recovery behavior.

## Why this release matters

Previous releases gave you a strong multi-chain ingestion engine. `v0.4.0` adds the operational layer around it:

- **Partition indexes** (`partitions.parquet`) are now part of the product, not just a side concept.
- **Verification** is easier to run, easier to explain, and easier to publish for later audits.
- **Recovery and merge behavior** are safer for larger or longer-lived runs.

For teams doing recurring backfills, replay jobs, or validation-heavy data pipelines, this release removes a lot of manual glue.

## Highlights for new users

### 1. Safer ingestion defaults and recovery guardrails

Streaming jobs now recover more predictably when a Firehose endpoint goes quiet or reconnect attempts drag on.

- Added reconnect recovery defaults and stall guardrails.
- Added clearer recovery-focused operational documentation.
- Reduced the chance of silent hangs during long backfills.

Example:

```bash
firehose-parquet \
  --endpoint https://eth.firehose.pinax.network:443 \
  --start-block 19000000 \
  --stop-block 19001000 \
  --output ./output \
  --stream-idle-timeout-secs 120 \
  --reconnect-stall-timeout-secs 900
```

This is especially helpful if you are running unattended jobs and want the process to fail fast instead of hanging forever during a bad reconnect cycle.

### 2. Verification is now a complete workflow, not just a low-level check

`verify` grew from a bootstrap command into a more complete surface with profiles, chain-aware hashing, richer EVM checks, and publishable JSON reports.

New capabilities include:

- bootstrap verify CLI + Merkle root registry,
- protocol-level EVM block verification,
- EVM transactions/logs/calls verification coverage,
- cross-chain hash strategy abstraction,
- profile-based verify UX,
- standardized report contract,
- documented artifact publication guidance.

Examples:

```bash
# Standard verification for an EVM blocks table
firehose-parquet verify ./output/evm/mainnet/blocks \
  --chain evm \
  --table blocks

# Fast, low-cost verification run
firehose-parquet verify ./output/evm/mainnet/blocks \
  --profile quick

# Ask for explicit check families
firehose-parquet verify ./output/evm/mainnet/transactions \
  --chain evm \
  --table transactions \
  --checks roots,protocol

# Override the automatic hash choice
firehose-parquet verify ./output/bitcoin/mainnet/blocks \
  --chain bitcoin \
  --table blocks \
  --hash-strategy sha256

# Publish the run report to the suggested artifact path
firehose-parquet verify ./output/evm/mainnet/blocks \
  --chain evm \
  --table blocks \
  --publish-report
```

For new users, the practical rule is:

- use `--profile quick` when you want a lightweight integrity pass,
- use the default `standard` profile for normal verification,
- publish reports when you want durable audit artifacts.

### 3. Partition indexes are now first-class

This release introduces a cohesive `partitions` workflow around canonical `partitions.parquet` files.

You can now:

- build partition indexes directly from Firehose,
- query them,
- validate them,
- shard them across workers,
- resolve exact ingestion windows from them,
- resume index builds,
- accelerate lookups with an optional sidecar.

#### Build a canonical partition index

```bash
firehose-parquet partitions build \
  --endpoint https://eth.firehose.pinax.network:443 \
  --chain eth-mainnet \
  --start-block 10000000 \
  --stop-block 10020000 \
  --partition-types day,hour \
  --output ./output
```

#### Resume an existing index build

```bash
firehose-parquet partitions build \
  --endpoint https://eth.firehose.pinax.network:443 \
  --chain eth-mainnet \
  --start-block 10000000 \
  --stop-block 10040000 \
  --partition-types day,hour \
  --output ./output \
  --resume
```

#### Write a low-latency lookup sidecar during build

```bash
firehose-parquet partitions build \
  --endpoint https://eth.firehose.pinax.network:443 \
  --chain eth-mainnet \
  --start-block 10000000 \
  --stop-block 10020000 \
  --partition-types day,hour \
  --output s3://my-bucket/firehose \
  --write-lookup-sidecar \
  --json
```

#### List index rows

```bash
firehose-parquet partitions ls \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --limit 50
```

#### Validate index continuity and invariants

```bash
firehose-parquet partitions validate \
  --partitions-index ./output/eth-mainnet/partitions.parquet
```

#### Assign partitions deterministically across workers

```bash
firehose-parquet partitions shard \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --shard-count 4 \
  --shard-index 1
```

#### Resolve one partition to exact block bounds

```bash
firehose-parquet partitions resolve \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --partition-value '2015-07-30 15:00:00' \
  --partition-chain eth-mainnet
```

#### Run ingestion over a partition window without hand-written block math

```bash
firehose-parquet \
  --endpoint https://eth.firehose.pinax.network:443 \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --partition-from '2015-07-30 14:00:00' \
  --partition-to '2015-07-30 18:00:00' \
  --partition-chain eth-mainnet
```

#### Use deterministic cursor paths for partition workers

```bash
firehose-parquet \
  --endpoint https://eth.firehose.pinax.network:443 \
  --cursor-template 'cursor/{chain}/{partition_type}/{partition_value}.parquet' \
  --partitions-index ./output/eth-mainnet/partitions.parquet \
  --partition-type hour \
  --partition-value '2015-07-30 15:00:00' \
  --partition-chain eth-mainnet
```

If you are new to the tool, this is one of the most important changes in the release. Instead of manually calculating block ranges, you can treat partitions as reusable scheduling units.

### 4. Faster and safer partition lookups

Optional `partitions.lookup.json` sidecars can now accelerate `partitions resolve`, while fingerprint checks prevent stale sidecars from being trusted after the canonical parquet index changes.

That means:

- better latency for repeated resolve calls,
- safer fallback behavior when the sidecar is outdated,
- automatic refresh behavior during noop resume builds.

There is no separate command to learn here beyond `--write-lookup-sidecar`; the rest is automatic once the sidecar exists next to `partitions.parquet`.

### 5. Better merge behavior for large datasets

The `merge` workflow received a set of reliability improvements for large or S3-backed datasets.

Improvements include:

- sequential table/partition processing to bound memory usage,
- streaming partition writes for larger datasets,
- clearer S3 retry and file-context logging.

Example:

```bash
firehose-parquet merge s3://my-bucket/evm/blocks \
  --flush-bytes 536870912
```

This is mostly an operational improvement rather than a new command surface, but it matters a lot if you have existing datasets with many small part files.

## Upgrade guidance

If you are adopting `v0.4.0` fresh:

- start with normal ingestion into a partitioned output directory,
- generate `partitions.parquet` for the chain(s) you care about,
- use `partitions resolve` or partition windows for scheduled workers,
- add `verify` as a post-ingestion validation step,
- publish reports if your team needs audit trails or repeatable QA evidence.

If you are upgrading from `v0.3.x`:

- keep using your existing ingestion flow,
- move partition-driven automation toward the `partitions` subcommand family,
- prefer verify profiles over hand-curated verify invocation patterns,
- enable sidecar generation if you frequently resolve from large partition indexes.
