# Validation follow-ups: EVM golden tests (findings 16-17)

Part of the validation follow-ups recorded in
[`validation-misc-followups.md`](validation-misc-followups.md) (#463). The
original golden-block regression is [#499](499-evm-golden-fixture.md).

## 16: owned mapping path

**Finding.** `blocks/tests/evm_golden.rs` called only the borrowed
`map_block(&[u8])`. Production ingestion has mapped owned buffers through
`map_block_bytes` since #518 / PR #606, so the golden test did not exercise the
path that writes production output.

**Fix.** The test takes a list of fixtures. In every one of the eight
configurations (standard/extended, Binary/Hex, with and without `fork_step`),
`map_both_ways` maps the payload through `map_block` and through
`map_block_bytes(Bytes::from_static(..))`, then requires the same table set,
equal schemas and equal `RecordBatch`es before the oracle checks run on the
result.

## 17: EIP-7702 fixture with a failed SET_CODE transaction

**Finding.** The retained block (26,049,575) had no `set_code_authorizations`,
`code_changes` or `gas_changes` rows and no failed `SET_CODE` transaction.

**Capture.** Ethereum mainnet block 26,000,004 was fetched once with the
documented helper, `blocks/examples/refresh_evm_golden.rs --block 26000004
--api-key-envvar SUBSTREAMS_API_KEY`, against
`https://eth.firehose.pinax.network:443`. Other Pinax credential variables were
unset for that run, so only the `X-Api-Key` header was sent; `.env` was not
read, and no credential or cursor is retained. The helper needed no changes.

**Storage.** The 5,304,418-byte payload (SHA-256
`ded7e47245becdf20d4b213a43d29cf3828140313e54fd8c849286b039178893`) is stored
as `blocks/tests/fixtures/evm-mainnet-26000004/block.pb.zst` (`zstd -19`,
762,362 bytes). The helper's `metadata.json` is unchanged and describes the
decompressed payload; the test decompresses with the `zstd` 0.14 crate (already
in the lockfile through parquet, now a `blocks` dev-dependency) and checks the
length and checksum. The checksum was re-verified with the `zstd` CLI.

**Independent oracle.** The payload was decoded with Python protobuf using a
descriptor generated by `protoc` from `proto/ethereum.proto`; the Rust mapper
was not involved. The block has 397 transactions (391 succeeded, one failed at
index 193, five reverted), seven `SET_CODE` transactions with 16 accepted
authorizations, 10 transaction code changes (five EIP-7702 delegation
designators and five `CREATE` deployments), 2,785 logs, 16 withdrawals and four
system calls. Transaction 130 is a reverted `SET_CODE` transaction with two
accepted authorizations (nonces 1,235 and 1,236) from authority
`0x3c27c4d588170b79e07941de57229e972cb02f37`; its root call records the gas
buy, gas refund, fee payment, the sender's nonce change and two authority nonce
changes, and no code change.

The oracle applies the documented persistence rules to the decoded data:
counts for all 20 tables (14,001 extended rows) and 304 values on 27 selected
rows, each naming its protobuf source path. The generator is retained as
[`499-evm-golden-oracle.py`](499-evm-golden-oracle.py) and regenerates
`expected.json` byte for byte. The mapper matched it on the first run, and a
deliberate one-value change to `expected.json` made the test fail. No mapper
code changed.

**Targeted check.** `mainnet_reverted_set_code_transaction_keeps_only_persistent_changes`
asserts transaction 130's raw shape (reverted, `SET_CODE`, two non-discarded
authorizations from one 20-byte authority, a reverted root call without code
changes) and its output: two authorization rows, three nonce rows (sender plus
one per accepted authorization), three balance rows, three call rows, and no
code, storage or gas rows.

## Limits

- Neither retained block records a gas change in any call; the current Pinax
  Ethereum producer emitted none in these blocks. `gas_changes` therefore still
  has no real-data coverage, and synthetic unit tests remain its only check.
- One additional block qualifies these mappings for that block's fork rules
  only; it is not proof for every Ethereum fork or producer.
